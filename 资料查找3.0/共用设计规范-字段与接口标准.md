## 一、HTTP 状态码

### 1.1 成功类（2xx）

| 状态码 | 含义 | 使用场景 |
| --- | --- | --- |
| `200 OK` | 请求成功 | GET 查询、PATCH 部分更新 |
| `201 Created` | 创建成功 | POST 创建新资源 |
| `204 No Content` | 成功但无返回体 | DELETE 删除成功、dismiss 关闭提醒 |

### 1.2 客户端错误（4xx）

| 状态码 | 含义 | 使用场景 |
| --- | --- | --- |
| `400 Bad Request` | 请求参数不合法 | 缺少必填字段、时间格式错误、数值超出范围 |
| `401 Unauthorized` | 未认证 | Token 缺失或过期 |
| `403 Forbidden` | 无权限 | Token 有效但无权访问该资源 |
| `404 Not Found` | 资源不存在 | schedule_id 或 reminder_id 对应的记录不存在 |
| `409 Conflict` | 资源冲突 | 创建日程时检测到时间冲突（`conflict_strategy = "prompt"` 且未 force） |
| `422 Unprocessable Entity` | 参数语义错误 | 业务规则校验失败（如对已取消的日程执行 update） |
| `429 Too Many Requests` | 频率限制 | 短时间大量请求 |

### 1.3 服务端错误（5xx）

| 状态码 | 含义 | 使用场景 |
| --- | --- | --- |
| `500 Internal Server Error` | 服务器内部错误 | 存储读写异常、未预期的运行时错误 |
| `503 Service Unavailable` | 服务不可用 | 数据库连接失败、依赖的外部服务不可达 |

## 二、响应体格式

### 2.1 成功响应

```json
HTTP/1.1 200 OK
Content-Type: application/json

{
  "code": 0,
  "message": "success",
  "data": { ... },
  "request_id": "req_a1b2c3d4"
}
```

```json
HTTP/1.1 201 Created
Content-Type: application/json

{
  "code": 0,
  "message": "success",
  "data": {
    "id": 1,
    "event": "项目周会",
    "start_time": "2026-07-28T10:00:00+08:00"
  },
  "request_id": "req_a1b2c3d4"
}
```

```json
HTTP/1.1 204 No Content
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | string | 业务状态码。`"success"` = 成功，其他 = 错误类型字符串 |
| `message` | string | 人类可读的简短描述 |
| `data` | object \| array \| null | 业务数据。创建/查询返回对象或数组，删除返回 null |
| `request_id` | string | 请求追踪 ID，格式 `req_` + 8 位随机十六进制。用于日志关联 |

### 2.2 错误响应

```json
HTTP/1.1 404 Not Found
Content-Type: application/json

{
  "code": "SCHEDULE_NOT_FOUND",
  "message": "日程不存在",
  "error": {
    "type": "SCHEDULE_NOT_FOUND",
    "details": {
      "schedule_id": 5
    }
  },
  "request_id": "req_a1b2c3d4"
}
```

```json
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{
  "code": "SCHEDULE_ALREADY_CANCELLED",
  "message": "该日程已被取消，无法修改",
  "error": {
    "type": "SCHEDULE_ALREADY_CANCELLED",
    "details": {
      "schedule_id": 5,
      "current_status": "cancelled"
    }
  },
  "request_id": "req_a1b2c3d4"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | string | 业务错误码（见第三节），值为 `error.type` 字符串 |
| `message` | string | 人类可读的中文错误描述 |
| `error.type` | string | 机器可读错误类型，大写+下划线 |
| `error.details` | object | 可选的错误上下文（无效参数名/值、当前状态等） |
| `request_id` | string | 同成功响应 |

## 三、业务错误码（`code` 字段）

### 3.1 编码规则

使用稳定字符串码，不与 HTTP 状态码耦合。格式：`<ENTITY>_<PROBLEM>`。

| 组成部分 | 说明 | 示例 |
| --- | --- | --- |
| ENTITY | 实体名（SCHEDULE/REMINDER/RECURRING/UNDO/MEMO） | `SCHEDULE` |
| PROBLEM | 问题类型（NOT_FOUND/CONFLICT/ALREADY_CANCELLED 等） | `NOT_FOUND` |

> 不推荐将 HTTP 状态码编码进业务错误码。HTTP 状态码独立表达传输语义，业务码表达领域错误——两者解耦。

### 3.2 错误码表

| HTTP | error.type | message |
| --- | --- | --- |
| 200/201/204 | （无） | `"success"` |
| 400 | `INVALID_PARAMETER` | 请求参数不合法 |
| 404 | `SCHEDULE_NOT_FOUND` | 日程不存在 |
| 404 | `REMINDER_NOT_FOUND` | 提醒不存在 |
| 409 | `SCHEDULE_CONFLICT` | 日程时间冲突 |
| 422 | `SCHEDULE_ALREADY_CANCELLED` | 日程已被取消 |
| 422 | `REMINDER_ALREADY_DISMISSED` | 提醒已关闭 |
| 422 | `REMINDER_ALREADY_SNOOZED` | 提醒已推迟 |
| 422 | `UNDO_WINDOW_EXPIRED` | 撤销窗口已过 |
| 422 | `NO_MORE_UNDO` | 无更多可撤销操作 |
| 422 | `INVALID_TIME` | 时间不合法 |
| 422 | `BUSINESS_RULE_VIOLATION` | 违反业务规则 |
| 429 | `RATE_LIMITED` | 请求过于频繁 |
| 500 | `INTERNAL_ERROR` | 服务器内部错误 |
| 503 | `SERVICE_UNAVAILABLE` | 服务暂不可用 |

> 响应体中 `code` 字段统一用 `error.type` 的字符串值，不再使用数字编码。HTTP 状态码独立表达传输语义。

## 四、ID 设计

| 上下文 | 命名 | 类型 | 示例 |
| --- | --- | --- | --- |
| 数据库主键 | `id` | INTEGER AUTOINCREMENT | `1` |
| API 响应中的 ID | `id` | number | `{"id": 1}` |
| API 请求中的外键 | `<entity>_id` | number | `{"schedule_id": 1}` |

> 在自己的 JSON 对象内用 `id`，跨实体引用用 `<entity>_id`。
> 数据库统一 `INTEGER AUTOINCREMENT`，API 输出 `number`。
> 不兼容 PR #70 的 `TEXT` ID 方案——若未来需多设备同步，在 MS3 前统一迁移到 UUID v7（TEXT），届时修改主外键和事件载荷。

## 五、时间字段

### 5.1 时间字段按表类别定义

| 表类别 | `created_at` | `updated_at` | `deleted_at` | 说明 |
| --- | --- | --- | --- | --- |
| **业务实体**（schedules, reminders, notes, recurring_series, recurring_instances） | ✅ | ✅ | ✅ | 完整审计 + 软删除 |
| **审计/回执**（undo_records, receipts） | ✅ | ❌ | ❌ | 只记录创建时间，不修改不软删 |
| **工作队列**（triggers, outbox, inbox） | ✅ | ❌ | ❌ | 只记录创建时间，通过状态流转管理生命周期 |

> 业务实体的 `deleted_at` 索引：`CREATE INDEX idx_<table>_deleted ON <table>(deleted_at) WHERE deleted_at IS NOT NULL`（部分索引，减少体积）。

```sql
created_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%f', 'now', '+8 hours') || '+08:00'),
updated_at TEXT NOT NULL DEFAULT (strftime('%Y-%m-%dT%H:%M:%f', 'now', '+8 hours') || '+08:00'),
deleted_at TEXT   -- NULL = 未删除
```

`updated_at` 需建触发器自动刷新：

```sql
CREATE TRIGGER <table>_updated_at AFTER UPDATE ON <table>
BEGIN
    UPDATE <table> SET updated_at = strftime('%Y-%m-%dT%H:%M:%f', 'now', '+8 hours') || '+08:00'
    WHERE id = NEW.id;
END;
```

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `created_at` | TEXT (ISO 8601) | 插入时自动 | 不可修改 |
| `updated_at` | TEXT (ISO 8601) | 插入+更新时自动 | 由触发器维护 |
| `deleted_at` | TEXT (ISO 8601) \| NULL | NULL | 软删除。查询默认 `WHERE deleted_at IS NULL` |

### 5.2 业务时间格式

| 场景 | 格式 | 示例 |
| --- | --- | --- |
| 完整时间 | ISO 8601（带时区） | `"2026-07-28T10:00:00+08:00"` |
| 纯时间 | `HH:MM` | `"17:00"` |
| 纯日期 | `YYYY-MM-DD` | `"2026-07-28"` |

> 统一 `+08:00`（北京时间），硬编码在数据库层。一期不考虑跨时区或用户时区快照。若后续需要多时区，改为存储 UTC + 应用层转换。

## 六、分页设计

### 6.8 一致性边界

偏移分页在读期间若发生写入（新增/取消日程），下一页可能出现重复或漏项。当前声明**弱一致性**：每次翻页为独立快照，不保证跨页无重复/无遗漏。VoiceLife 语音场景下，用户通常只看前 2-3 页，影响可控。

> 选择偏移分页（`page`/`page_size`）而非游标分页（`page_token`），原因：
> 1. ESP32 本地 SQLite，单用户数据量 < 10,000 条，偏移性能可接受
> 2. LLM Agent 调用时，`"第 2 页"` 比 `"下一页的 token 是 xxx"` 更自然
> 3. 语音播报场景下，用户说"下一页"可直接映射为 `page + 1`

### 6.1 请求参数

| 参数 | 类型 | 默认值 | 最小值 | 最大值 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `page` | integer | `1` | `1` | — | 页码。传 `0` 或负数时自动修正为 `1` |
| `page_size` | integer | `20` | `1` | `50` | 每页条数。超出 `50` 时截断为 `50`，传 `0` 时修正为 `20` |

### 6.2 排序

| 端点 | 默认排序 | 说明 |
| --- | --- | --- |
| `GET /schedules` | `start_time ASC` | 按开始时间升序（最近的在前面） |
| 其他列表端点 | `created_at DESC` | 按创建时间倒序（最新的在前面） |

> 一期不暴露排序参数。若后续需要，增加 `sort_by` + `sort_order`（`asc` / `desc`）。

### 6.3 响应格式（有数据）

```json
HTTP/1.1 200 OK

{
  "code": 0,
  "message": "success",
  "data": [
    { "id": 1, "event": "项目周会", ... },
    { "id": 2, "event": "看牙医", ... }
  ],
  "pagination": {
    "page": 1,
    "page_size": 20,
    "total": 57,
    "total_pages": 3,
    "has_more": true
  },
  "request_id": "req_a1b2c3d4"
}
```

### 6.4 响应格式（无数据）

```json
HTTP/1.1 200 OK

{
  "code": 0,
  "message": "success",
  "data": [],
  "pagination": {
    "page": 1,
    "page_size": 20,
    "total": 0,
    "total_pages": 0,
    "has_more": false
  },
  "request_id": "req_a1b2c3d4"
}
```

> 无数据时返回 `200` + 空数组 `[]`，不返回 `404`。`total_pages` 为 `0`。

### 6.5 响应字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `pagination.page` | integer | 当前页码（可能被修正，见 6.6） |
| `pagination.page_size` | integer | 实际使用的每页条数（可能被修正） |
| `pagination.total` | integer | 总记录数（不受 page/page_size 影响） |
| `pagination.total_pages` | integer | 总页数。`total = 0` 时为 `0` |
| `pagination.has_more` | boolean | 是否还有下一页。`page < total_pages` 时为 `true` |

### 6.6 边界处理

| 场景 | 行为 |
| --- | --- |
| `page=0` 或负数 | 自动修正为 `page=1` |
| `page > total_pages` | 返回空数组，`page` 在响应中回显传入值（不修正，调用方可据此判断越界） |
| `page_size=0` | 自动修正为默认值 `20` |
| `page_size > 50` | 截断为 `50` |
| `total = 0` | `total_pages = 0`，`has_more = false`，`data = []` |

### 6.7 语音场景约定

语音播报时，若 `total > page_size`：
- TTS 只播报前 `min(page_size, 3)` 条的关键信息
- 末尾追加"还有 N 条，我发到 IM 了"
- IM 回执中展示当前页完整列表。IM 卡片交互细节由 IM 模块独立设计，不在本规范中定义

## 七、枚举字段

- 小写字母 + 下划线：`"active"`、`"in_progress"`
- 数据库 TEXT + CHECK 约束，API 传字符串
- 不在代码中用整数映射——LLM 无法理解数字含义

```sql
status TEXT NOT NULL DEFAULT 'active'
    CHECK(status IN ('active', 'completed', 'cancelled'))
```

## 九、可选字段语义

| 场景 | 做法 |
| --- | --- |
| "不改这个字段" | 不传该键 |
| "清空这个字段" | 传 `null` |

```json
// 只改地点
{ "schedule_id": 1, "location": "302" }

// 清除备注
{ "schedule_id": 1, "notes": null }
```

数据库可为空的列用 `NULL`，不设空字符串默认值。

> `deleted_at` 适用于业务实体表（schedules、reminders、notes 等）。审计/队列表（undo_records、receipts、outbox、inbox）使用保留期 + 归档策略，不设 `deleted_at`——否则破坏去重证据和审计链。

## 十节（补充）：幂等性设计

语音交互场景下，用户可能在短时间内重复说出相同的指令（"明天十点开会"连续说两次）。若不处理，会创建两条相同的日程。

### 请求头

```
Idempotency-Key: <client_generated_uuid>
```

| 行为 | 说明 |
| --- | --- |
| 首次请求 | 正常处理，服务端记录 `key → response` 映射 |
| 重复请求（24h 内，相同 key） | 返回缓存的响应，**不重复执行** |
| 过期请求（>24h） | 视为新请求 |

### 实现要点

- Key 由客户端生成（UUID v4），每次独立操作使用不同的 key
- 服务端存 `key → (response_body, status_code, created_at)`，24h TTL
- 仅对写操作（POST/PATCH/DELETE）生效，GET 不需要

> ESP32 本地场景：若 Function Calling 由云端灵矽发起，幂等键由灵矽侧生成。若 ESP32 本地直接调用 L3 服务，幂等键由 ESP32 固件生成。
