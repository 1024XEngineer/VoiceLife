# 语音服务设计文档（按官方协议修订）

> 日期：2026-07-28
> 适用范围：VoiceLife 在 78/xiaozhi-esp32 上的语音接入
> 官方代码基线：78/xiaozhi-esp32@e0074e90
> 结论：本模块只负责板端音频处理和 XRobot 会话适配，不负责 LLM、日程规则、SQLite 或长期记忆。

这次重写先解决一个边界问题：灵矽 XRobot WebSocket 没有“设备发送一段文本，请服务端直接做 TTS”的标准消息。设备发的是 hello、listen、音频、abort 和 MCP 消息；服务端返回 stt、tts、llm、mcp 事件及音频。因此，PlayTts(text) 不能再被写成官方现成接口。

下一步：先按第 12 节把 WebSocket、板型 AEC 和端侧 MCP 跑通；验证前不进入实现承诺。

## 1. 模块边界

### 1.1 语音服务负责

- 麦克风采集、音频格式转换和 Opus/PCM 编解码；
- AFE、VAD、WakeNet 以及板型支持的 AEC；
- 播放服务端下发的 TTS 音频；
- 维护本设计已经核对过的 XRobot WebSocket 音频会话；
- 发送 listen、abort、唤醒词 detect 和端侧 MCP 消息；
- 把服务端 stt、tts、llm、mcp、notify 等控制消息转成应用事件，并保留未知消息的透传入口。

### 1.2 语音服务不负责

- LLM 推理和 Function Calling 编排；
- 日程、提醒、备忘录的业务规则；
- SQLite 表、事务和迁移；
- 灵矽长期记忆或聊天记录；
- IM 卡片发送；
- 本地提醒定时器。

这些能力由应用编排层、Schedule 服务、MCP 服务和持久化层分别负责。语音服务不直接连 Schedule、IM 或 SQLite。

## 2. 正确的整体关系

~~~text
麦克风 / 喇叭
      ↕ PCM
AudioEngine ⇄ XRobotTransport ⇄ WebSocket（WSS）⇄ 灵矽 XRobot
 AFE / VAD       │ JSON 事件                         │
 WakeNet / AEC   ▼                                  └── 云端 Agent / 记忆 / MCP Client
          ApplicationOrchestrator
                 ├── 应用事件 ──→ IM
                 └── 分发 MCP tools/call
                              ▼
                        端侧 MCP Server
                              ▼
                       ScheduleService
                              ▼
                 SQLite（若本地存储方案通过验证）
~~~

官方小智是端侧 MCP Server，云端是 MCP Client。云端通过 initialize、tools/list、tools/call 调用板端工具；日程工具的实现才会落到本地 Schedule 和 SQLite。不能把“ASR 文本 → 设备再调用云端 LLM → 设备自己做 Function Calling”写成小智官方链路。

本文只设计已经核对过的 WebSocket 通道。`xrobot-docs-archive` 的 MQTT 页面目前没有协议正文，小智基线的 MQTT 控制与 UDP 音频也不是 WebSocket 的同构替换，因此不在这里画成另一个已验证实现。

### 3.2 连接与握手

- WebSocket 默认候选地址为 wss://xrobo-io.qiniuapi.com/v1/ws/；如果 OTA 返回了动态地址，优先使用 OTA 地址。
- 握手头包含 Authorization、Device-Id、Client-Id 和 Protocol-Version；Protocol-Version 必须与 hello.version 一致。凭据来源、轮换和删除流程是项目自己的安全契约，不能假定官方已替我们完成。
- XRobot 协议允许 hello 声明 Opus 或 PCM。小智 `e0074e90` 的 WebSocket 适配器上行固定为 Opus、16 kHz、单声道、60 ms；服务端 hello 的 sample_rate/frame_duration 主要驱动下行解码，不能把“协议支持 PCM”写成当前小智适配器已经支持 PCM 上行。
- 只有实现了配置更新处理时，才在 hello 的 `features.notify.config_updated` 中声明 notify 能力；否则只保留未知控制消息透传，不承诺会收到该通知。
- 服务端 hello 的 session_id 是可选字符串。收到时原样保存，并在后续 listen、abort 和 mcp 消息中携带；缺省时不能生成本地替代值，字段应省略还是发送空串仍需真实服务验证。
- 当前小智代码等待服务端 hello 的超时是 10 秒，协议通道的空闲超时是 120 秒。其他重连、队列和请求超时属于 XE6-15 待验证策略。

### 3.3 设备发送的消息

~~~text
hello                         建立协议能力
listen state=start            开始上传一轮音频
listen state=stop             停止上传
listen state=detect           上报唤醒词
abort                         中断服务端当前说话
mcp                           返回或发送端侧 MCP JSON-RPC 消息
二进制帧                      上传 Opus/PCM 音频
~~~

### 3.4 服务端返回的事件

~~~text
hello                         会话和音频参数
stt                           用户语音识别文本
llm                           情绪或显示相关事件
tts state=start               服务端开始下发 TTS
tts state=sentence_start      文本句子事件
tts state=stop                服务端结束下发，含 is_aborted
mcp                           云端调用端侧工具
notify                        配置更新等服务端通知
二进制帧                      TTS 音频
~~~

小智基线还处理 system、alert 和可选 custom 等控制消息。Typed handler 只覆盖本设计关心的事件，其余 JSON 必须通过通用回调交给应用层，不能因为重写接口就静默丢掉。

官方协议没有 SendTts(text)。如果以后要接一个自建 TTS HTTP/WS 服务，可以另做 LocalTtsPort，定义 request_id、服务端 ACK、去重窗口和断线后的放弃策略；它不能复用本节的 XRobot WebSocket 契约。

## 4. 身份和事件关联

不要把远端 session_id、连接、代次、采集周期和本地 turn ID 混成一个字段。

~~~cpp
using ConnectionId = uint64_t;
using ConversationGeneration = uint64_t;
using CaptureEpochId = uint64_t;
using TurnId = uint64_t;

enum class AudioFormat { OPUS, PCM_S16LE };

struct TransportAudioFrame {
    ConnectionId connection_id;
    ConversationGeneration generation;
    AudioFormat format;
    uint32_t sample_rate;
    uint8_t channels;
    uint16_t frame_duration_ms;
    std::vector<uint8_t> payload; // 按协商参数编码的 Opus 或 PCM
    std::optional<uint32_t> timestamp_ms; // 仅协商支持时使用
};

struct RemoteSession {
    std::optional<std::string> session_id; // 服务端 hello 下发，可缺省
};

struct AsrEvent {
    ConnectionId connection_id;
    ConversationGeneration generation;
    CaptureEpochId capture_epoch_id;
    TurnId turn_id; // 收到 stt 时由本地生成，不上送服务器
    std::optional<std::string> remote_session_id;
    std::string text;
};

enum class CaptureEpochState {
    CAPTURING,
    AWAITING_RESULT,
    RESULT_RECEIVED,
    CANCELLED,
    FAILED,
};

enum class TransportErrorCode {
    HANDSHAKE_TIMEOUT,
    AUTH_REJECTED,
    TLS_FAILURE,
    TRANSPORT_CLOSED,
    PROTOCOL_ERROR,
    UNSUPPORTED_AUDIO_PARAMS,
    QUEUE_OVERFLOW,
    STT_WAIT_TIMEOUT,
    UNKNOWN,
};

struct CaptureEpochEvent {
    ConnectionId connection_id;
    ConversationGeneration generation;
    CaptureEpochId capture_epoch_id;
    std::optional<std::string> remote_session_id;
    CaptureEpochState state;
    std::optional<TransportErrorCode> error_code;
};

struct TransportErrorEvent {
    ConnectionId connection_id;
    ConversationGeneration generation;
    std::optional<CaptureEpochId> capture_epoch_id;
    std::optional<std::string> remote_session_id;
    TransportErrorCode code;
    bool retryable;
    std::string message;
};
~~~

remote_session_id 只表示 XRobot 服务端会话，generation 用来隔离重连前后的事件。capture_epoch_id 对应一次 listen start/stop 周期；realtime 模式可以在同一个 capture epoch 内返回多条 stt，每条到达时再分配本地 turn_id。它们都不会上送服务器，也不能伪装成官方 session_id。

## 5. 对外接口

接口只表达已经选定的职责，不把尚未存在的官方能力写进去。

~~~cpp
enum class ListeningMode { MANUAL, AUTO, REALTIME };

enum class StopReason { USER_STOP, VAD_END, CANCEL, DISCONNECT };
enum class ConnectionState { DISCONNECTED, CONNECTING, READY, FAULT };

struct ConnectionEvent {
    ConnectionId connection_id;
    ConversationGeneration generation;
    std::optional<std::string> remote_session_id;
    ConnectionState state;
    std::string message;
};

struct McpEvent {
    ConnectionId connection_id;
    ConversationGeneration generation;
    std::optional<std::string> remote_session_id;
    std::string payload;
};

struct ControlJsonEvent {
    ConnectionId connection_id;
    ConversationGeneration generation;
    std::optional<std::string> remote_session_id;
    std::string type;
    std::string payload;
};

struct ServerTtsEvent;

class SpeechTransport {
public:
    bool Connect();
    void Disconnect();

    bool SendAudio(const TransportAudioFrame& frame);
    bool SendWakeWordDetected(const std::string& text);

    // 返回本地 capture_epoch_id，不是远端 session_id。
    std::optional<CaptureEpochId> StartListening(ListeningMode mode);
    void StopListening(CaptureEpochId capture_epoch_id, StopReason reason);

    // 发送 XRobot abort；wake-word 打断时携带官方 reason 字段。
    enum class AbortReason { GENERIC, WAKE_WORD_DETECTED };
    bool AbortSpeaking(AbortReason reason = AbortReason::GENERIC);

    // 端侧 MCP Server 向云端回传 JSON-RPC 消息。
    bool SendMcpMessage(const std::string& payload);

    void OnAsr(std::function<void(const AsrEvent&)> callback);
    void OnCaptureEpoch(std::function<void(const CaptureEpochEvent&)> callback);
    void OnTransportError(std::function<void(const TransportErrorEvent&)> callback);
    void OnAudio(std::function<void(const TransportAudioFrame&)> callback);
    void OnServerTts(std::function<void(const ServerTtsEvent&)> callback);
    void OnMcp(std::function<void(const McpEvent&)> callback);
    void OnControlJson(std::function<void(const ControlJsonEvent&)> callback);
    void OnConnection(std::function<void(const ConnectionEvent&)> callback);
};
~~~

### 5.1 语音输入

StartListening() 只开始本地采集和官方 listen state=start。AudioEngine 通过 SendAudio() 上传二进制帧；下行二进制帧经 OnAudio() 交给解码播放。官方 stt 消息没有 capture/turn ID，也没有“部分结果/最终结果”字段，本地事件不能虚构 `is_final` 或服务端关联键。

Transport 在回调 OnAudio() 前校验 frame 的 connection_id/generation，重连后残留在队列里的旧帧直接丢弃；上行帧也必须标记当前连接，不能跨 generation 发送。

manual/auto 模式同一连接最多保留一个未结束的 capture epoch。`USER_STOP` 或 `VAD_END` 会发送 listen state=stop，并进入 `AWAITING_RESULT`；随后第一条 stt 归入这一周期并发出 `RESULT_RECEIVED`。等待计时从 stop 发出后开始，在 stt、取消或连接关闭时结束；超时值由项目实测配置，不冒充官方参数。超时后若要立即开始下一周期，同样先重建音频通道。

realtime 模式是一段长 capture epoch，每收到一条 stt 才生成新的本地 turn_id。`CANCEL` 先发送 listen state=stop（通道可用时），然后关闭音频通道并重新 hello，拿到新的 connection/remote session 后才能开始下一周期；只在本地递增 generation 不能隔离旧连接的迟到 stt。断线进入 `FAILED`，状态变化通过 CaptureEpochEvent 发出。

`DISCONNECT` 没有可用通道时不再补发控制帧，只完成本地 `FAILED` 收尾。

### 5.2 语音输出

语音服务消费服务端 tts 事件和二进制音频：

~~~cpp
enum class ServerTtsState { START, SENTENCE_START, STOP };

struct ServerTtsEvent {
    ConnectionId connection_id;
    ConversationGeneration generation;
    std::optional<std::string> remote_session_id;
    ServerTtsState state;
    std::optional<bool> is_aborted; // 仅 STOP 事件有意义
    std::optional<std::string> text; // 仅 SENTENCE_START 事件有意义
};
~~~

AbortSpeaking() 发送官方 abort；唤醒词打断时携带 `reason: wake_word_detected`。收到 `tts stop` 且 `is_aborted=true` 后立即清空解码/播放缓冲；`is_aborted=false` 时先把播放状态置为 `DRAINING`，等已接收音频真正播完后再进入 `IDLE`。播放中断是一个事件，不是长期的全局会话状态，也不能用本地 play_id 伪造服务端 ACK。

如果产品必须让 Schedule 直接给一段文本并立刻播报，需另立一个自建 TTS 适配器。它至少要解决：请求 ID、提交点、ACK 丢失、重复播放、队列恢复和错误提示。在这个适配器落地前，PR79 不应依赖一个名为 PlayTts(text) 的“灵矽官方接口”。

## 6. AEC、VAD 和 WakeNet

### 6.1 AEC 是板型能力，不是语音服务默认保证

~~~cpp
enum class AecMode {
    OFF,
    SERVER_AEC,
    DEVICE_AEC,
};

struct AudioCapabilities {
    AecMode aec_mode;
    bool has_playback_reference;
    bool has_wake_word;
    bool supports_realtime_listening;
};
~~~

- SERVER_AEC：设备在 hello 的 `features.aec` 中请求服务端 AEC，但小智 Kconfig 将它标为 Unstable；必须同时确认 OTA/协议版本、服务端支持和带 playback timestamp 的二进制路径（参考协议 v2）后才能启用。只发 `features.aec=true` 不等于 AEC 已生效。
- DEVICE_AEC：只有 codec 提供同步 playback reference channel 时才允许启用。小智官方 AFE 会检查 codec_->input_reference()；没有该通道不能宣称支持设备 AEC。
- OFF：没有可用 AEC 时采用半双工或明确接受回声风险。

设备 AEC 的 reference 必须来自实际播放链路的参考通道，不能只画一条“解码 PCM 回送”就算完成。需要在目标板上测量采样率、声道、帧大小、硬件延迟和 buffer 欠载/溢出。软件缓存回采只能作为待验证实验路径。

### 6.2 WakeNet 不保证始终运行

小智是否在 listening 或 speaking 阶段保持唤醒检测，受板型、AFE、配置项和 AEC 能力影响。设计拆成四个正交状态：

~~~text
WakeWord:   DISABLED / ENABLED / TRIGGER_SUPPRESSED
Capture:    IDLE / LISTENING
Playback:   IDLE / RECEIVING / PLAYING / DRAINING
Cloud:      DISCONNECTED / CONNECTING / READY / FAULT
~~~

WakeWordDetected 是事件，不是一个永久状态。应用收到它后，根据当前板型能力决定是否发送 abort、是否发送 listen state=detect、是否开启下一轮录音。应用层只需切换“允许触发新会话”的许可，不要把这件事写成底层 WakeNet 被销毁或重启。

## 7. 实时任务和背压

先固定协作关系，再给目标板定数字。当前不把 4×60ms 或某个固定任务优先级写成通用结论。

~~~text
Capture/AFE task       采集、AEC/VAD/WakeNet
Encode/send task       音频帧编码和发送队列
Receive/decode task    TTS 接收、解码、播放队列
Protocol/app task      JSON 事件、MCP、状态转换
~~~

约束：

- 音频任务不能等待网络或数据库；
- 队列必须有上限，满载时记录计数并按策略丢帧或结束当前 capture epoch；
- 网络发送失败不能让编码任务永久阻塞；
- 播放欠载要记录 underrun，不发成功的播放 drain 事件；
- JSON/MCP 回调不能反向阻塞采集任务；
- 队列容量、任务栈、PSRAM 使用量和端到端延迟在目标板压测后定值。

验收至少包括：连续播放时唤醒/打断、Wi-Fi 抖动、服务端断开、队列满载、旧代次事件到达，以及 AEC reference 缺失时的降级。

## 8. 状态转换

不再使用一个枚举描述所有并行状态。应用可以读取一个快照：

~~~cpp
enum class WakeWordState { DISABLED, ENABLED, TRIGGER_SUPPRESSED };
enum class CaptureState { IDLE, LISTENING };
enum class PlaybackState { IDLE, RECEIVING, PLAYING, DRAINING };

struct SpeechSnapshot {
    ConnectionState cloud;
    WakeWordState wake_word;
    CaptureState capture;
    PlaybackState playback;
    ConversationGeneration generation;
};
~~~

关键事件：

| 事件 | 处理 | 结果 |
| --- | --- | --- |
| 服务端 hello | 保存可选 remote_session_id 和音频参数 | Cloud=READY |
| 本地唤醒词命中 | 由应用决定 detect/abort/start | 新 capture_epoch_id |
| listen start | 开启采集和上传 | Capture=LISTENING |
| 服务端 stt | 发出 AsrEvent；manual/auto 结束等待，realtime 保持 capture epoch | 不在音频模块做 LLM |
| 服务端 tts start | 清理旧解码状态，接收音频 | Playback=RECEIVING/PLAYING |
| tts stop，is_aborted=true | 清理解码和播放队列 | Playback=IDLE |
| tts stop，is_aborted=false | 等待已接收音频播完 | Playback=DRAINING→IDLE |
| 断线 | 递增 generation，丢弃旧事件 | Cloud=FAULT |

打断由 abort 和 `tts stop/is_aborted` 表达，不再用一个单一全局枚举承载它；需要给 UI 展示时，单独发应用事件。

## 9. MCP、Schedule、SQLite 和记忆

用户说“明天七点开会”时，官方链路应是：

~~~text
WakeNet → listen start → 音频 → 云端 STT/Agent
                                  ↓ MCP tools/call
                         端侧 ScheduleService
                                  ↓
                         SQLite 业务事实库
                                  ↓ MCP result
                         云端 Agent 生成回复
                                  ↓ tts 事件 + 音频
                         板端解码和播放
~~~

- Schedule 工具由端侧 MCP Server 注册，工具实现可以调用本地 SQLite；
- 语音服务只转发音频和协议事件，不读表、不写表；
- IM 回执由应用编排层根据业务结果发送，不由音频模块直接发送；
- 灵矽长期记忆属于云端 Agent 能力，使用 agent_id + identify_id、memory/infer、memory/recall 等接口；它不是板端音频缓存，也不是 SQLite 的别名；
- 本地提醒定时器属于 Schedule。提醒到期后如何让官方云端会话主动播报，当前资料没有一个可直接调用的 PlayTts(text) 标准接口，必须另做平台能力确认或接入自建 TTS 适配器。

## 10. 连接安全和错误契约

以下是项目必须补齐的边界，不冒充官方已经规定：

| 错误 | 是否可重试 | 上层动作 |
| --- | --- | --- |
| HANDSHAKE_TIMEOUT | 是 | 关闭连接，按项目退避策略重连 |
| AUTH_REJECTED | 否，先更新凭据 | 提示绑定/凭据失效 |
| TLS_FAILURE | 否或延迟重试 | 检查时间、主机名和根证书 |
| TRANSPORT_CLOSED | 是 | 递增 generation，丢弃旧事件 |
| UNSUPPORTED_AUDIO_PARAMS | 否 | 仅在无法重采样或解码时结束会话，记录服务端参数 |
| QUEUE_OVERFLOW | 视队列而定 | 丢帧或结束当前 capture epoch |
| STT_WAIT_TIMEOUT | 是 | 结束当前 capture epoch；重开前先换新 connection |
| PROTOCOL_ERROR | 否 | 断开并保留诊断信息 |

安全要求：

- URL 优先来自 OTA；固定 WSS 只是默认候选；
- OTA 返回的 scheme 不能无条件信任：生产只接受 `wss://`，明文 `ws://` 仅在受控开发网络明确放行；
- TLS 要做证书链、主机名和根证书更新策略；设备时间不可信时要定义校验策略；
- Token 的注入、轮换、失效和清除要有明确流程；没有配置证据时不写“已启用 NVS 加密分区”；
- 日志不打印 Token、完整 ASR 文本、日程标题或原始音频；
- MCP 工具重试不得在业务层造成重复写入，幂等由 Schedule/SQLite 事务契约保证。

当前官方可直接确认的超时只有服务端 hello 等待和协议通道空闲超时。1/2/4/8 秒重连、30 秒 ping/pong、10 秒 ASR/TTS 请求超时等数字，先放到目标板实验配置，不放在官方协议栏里。

## 11. 与其他 PR 的接口调整

| 对象 | 本文结论 |
| --- | --- |
| PR79 Schedule | 不再直接依赖“灵矽 PlayTts(text)”；通过端侧 MCP 工具和应用编排层接入。提醒主动播报路径需另立方案。 |
| PR78 IM | 由应用编排层并行发送，IM 不读取语音服务内部状态。 |
| PR70 L5/SQLite | 由 Schedule 或 MCP 工具实现访问，语音服务不访问。SQLite 不是 AI 长期记忆。 |
| 灵矽长期记忆 | 云端 Agent 侧能力，由身份适配器管理，不放入音频模块。 |

## 12. 实现前必须验证的事项

1. 在目标板上确认 AEC 模式：设备回采、服务端 AEC 还是半双工。
2. 用官方 hello/listen/abort/mcp 流程跑通真实灵矽连接，记录服务端是否下发 session_id 和实际音频参数。
3. 确认端侧 Schedule MCP 工具的注册、调用和 SQLite 事务边界。
4. 另行决定提醒到期后的主动播报路径，不把 PlayTts(text) 偷塞回 XRobot 协议。
5. 压测 Wi-Fi 抖动、断线、队列满载、TTS 欠载和旧 generation 事件。
6. 评估 Token 生命周期、OTA 动态地址和 TLS 根证书更新。
7. 实测服务端 hello 缺省 session_id 时，后续消息应省略字段还是发送空串；不得用本地 ID 填充。
8. 实测 MCP JSON-RPC `id` 的 number/string 兼容性；官方文档允许两者，小智基线解析器只接受 number 时要补兼容层或约束平台输入。

在这些事项完成前，这份文档只作为接口边界和验证清单，不作为“全双工、板端 AEC、固定重连参数或本地 TTS 已经可用”的实现承诺。
