# 设计审查报告：日程管理接口 × 企微IM通道 × 持久化层

> 日期：2026-07-27
> 审查对象：PR #79（日程管理接口）、PR #78（企微 IM 通道）、PR #70（L5 持久化层）
> 审查维度：跨文档一致性、逻辑完整性、字段规范

---

## 一、跨文档一致性

### 1.1 Reminder 状态机不一致（严重）

这是三个文档之间最大的矛盾。

| 文档 | Reminder 状态值 |
| --- | --- |
| PR #79（接口文档） | `pending` → `triggered` → `snoozed` / `dismissed` |
| PR #70（持久化层） | `pending` → `pushed` → `closed` / `delayed` / `multi-delayed` |

两个文档对同一实体的状态命名完全不同。`triggered` vs `pushed`、`dismissed` vs `closed`、`snoozed` vs `delayed`。调用方（LLM Agent）按 #79 理解状态机，但底层存储按 #70 建表和 CHECK 约束——两个不兼容的状态集会直接导致写入失败。

**建议**：两方对齐，#70 的状态值应改为与 #79 一致（`pending` / `triggered` / `snoozed` / `dismissed`）。`multi-delayed` 如果确实需要可保留为内部状态，不对外暴露。

### 1.2 Schedule vs CalendarEvent 实体拆分不一致

| 文档 | 单次/周期处理方式 |
| --- | --- |
| PR #79 | 单一 Schedule 实体，不区分单次和周期 |
| PR #70 | 三表拆分：`calendar_events`（单次）+ `recurring_series`（系列）+ `recurring_instances`（实例） |

#79 的 `create_schedule` 没有周期相关参数，而 #70 已经设计好了周期系列和实例表。#79 缺少 `recurrence` 参数（如"每周五"），意味着当前 API 不支持周期日程创建——但原型文档（P1/P2/P3）明确要求支持。这是功能缺口。

**建议**：#79 的 Schedule 模型增加 `recurrence` 字段（null 表示单次，非 null 表示周期规则），`update_schedule` 增加 `scope` 参数（仅本次/本次及以后/整个系列）。

### 1.3 撤销/Undo 机制在接口文档中缺失

| 文档 | 撤销支持 |
| --- | --- |
| PR #79 | 无 undo 接口 |
| PR #70 | `undo_records` 表 + Repository 接口已设计 |
| P3 原型文档 | 明确要求 15 分钟内可撤销 |

#70 已经把撤销记录表设计好了，但 #79 没有暴露 `undo_last_operation` 接口。上层 LLM 无法调用撤销能力。

**建议**：#79 增加 `undo_last_operation` 接口，入参为空，返回恢复后的实体。

### 1.4 IM 通道的事件类型未与 Schedule 领域事件对齐

PR #78 提到"业务事件"驱动 IM 推送，但 #79 和 #70 都没有定义领域事件类型。三个文档各自为政：
- #79 的 `reminder_triggered` 事件只定义了提醒触发一种
- #78 需要创建、修改、删除、跳过、推迟等多种事件
- #70 没有事件定义

**建议**：统一在 #79 或独立文档中定义领域事件枚举，三份文档共同引用。

## 二、逻辑问题

### 2.1 create_schedule 的 `ignore_conflict` 参数直接跳过确认

当前设计：`ignore_conflict = false`（默认）时返回冲突列表让 LLM 处理，`true` 时静默创建。但 LLM 的二次调用可能在网络延迟或并发场景下导致竞态——用户说"还是创建"时，中间另一条日程已被创建，冲突仍然存在但 `ignore_conflict=true` 直接写入了。

**建议**：增加 `conflict_strategy` 枚举替代 boolean：`"prompt"`（提示确认）、`"force"`（强制覆盖）、`"cancel"`（拒绝）。`force` 模式下仍返回冲突列表但已创建。

### 2.2 update_schedule 的 `reminders` 是全量替换而非增量

文档明确说"传入此参数会完全替换现有提醒列表"。如果用户说"帮我再加一条5分钟前的提醒"，LLM 需要先查询现有提醒列表，拼上新的，再全量传入——两次网络调用 + 中间状态可能变化。

**建议**：保留 `add_reminder` 和 `delete_reminder` 的独立接口用于增量操作，`update_schedule` 的 `reminders` 字段改为"仅当传入时才替换，不传入时保持原值"。

### 2.3 没有"记一件事"（Memo）的接口

P1 原型明确包含"记一件事"（无时间维度的记录，如停车位、取件码）。#79 完全没有 Memo 相关接口，#70 有 `temp_notes` 表和 24h TTL。但 `temp_notes` 的 24 小时过期不适用于所有备忘录场景（"车停哪了"不应该 24 小时后自动消失）。

**建议**：#79 增加 `create_note` / `query_notes` 接口。`temp_notes` 的 TTL 应可配置（0 = 永不过期）。

### 2.4 IM 通道的回调安全性——token 验证细节缺失

PR #78 提到"每个按钮绑定短期、一次性的服务器签发 token"，但 #79 没有任何 token 生成或验证接口。IM 回调的验签逻辑落在哪个模块？token 如何与 schedule_id 关联？

**建议**：#79 增加 `generate_action_token` 接口，返回一次性授权 token，IM 模块回调时传入，schedule 模块验签后执行。

## 三、字段设计问题

### 3.1 status 泛滥且语义混乱

统计三个文档中的 status 字段：

| 文档 | 实体 | status 值 | 问题 |
| --- | --- | --- | --- |
| #79 | Schedule | `active`, `cancelled` | 缺少 `completed`——日程过了时间算完成还是保持 active？ |
| #79 | Reminder | `pending`, `triggered`, `snoozed`, `dismissed` | 与 #70 不兼容 |
| #70 | RecurringSeries | `active`, `paused`, `terminated` | `paused` 是临时还是永久？缺少区分 |
| #70 | RecurringInstance | `active`, `skipped`, `modified` | `modified` 是状态还是操作类型？状态应该描述"这个实例现在什么状态"，而非"对它做了什么" |
| #70 | Reminder | `pending`, `pushed`, `closed`, `delayed`, `multi-delayed` | 5 个状态，`multi-delayed` 可以合并到 `delayed` + `delay_count` |
| #70 | Trigger | `scheduled`, `fired`, `cancelled` | 与其他文档无对应 |

### 3.2 `deleted_at` 软删除缺失

所有三个文档都使用硬删除或 status 字段标记取消。#79 的 `delete_schedule` 直接物理删除，#70 也没有 `deleted_at` 列。一旦误删，只能依赖 `undo_records` 恢复——但 undo 有 15 分钟窗口限制。

**建议**：所有实体表统一加 `deleted_at TIMESTAMP NULL`，查询时默认 `WHERE deleted_at IS NULL`。`undo_records` 的撤销窗口基于 `deleted_at` 而非物理删除。

### 3.3 #70 的 SQLite 时间存储方案不一致

#70 说"时间统一存 ISO 8601 字符串"，但 SQLite 没有原生 datetime 类型，存字符串有以下问题：
- 无法用 SQL 做时间比较（`WHERE start_time > '...'` 依赖字符串字典序，ISO 8601 格式下勉强可用但不标准）
- 无法用 `strftime` 做日期分组（需额外转换）

**澄清**：规范化为同一时区、固定格式的 ISO 8601 TEXT 在 SQLite 中可以按字典序排序，SQLite 日期函数也可解析。真正的风险是混合时区偏移或格式不统一。当前规范已统一为 `+08:00`，此问题可控。
