# PR #59 Proposal 审查与原型决策

## 结论

PR #59 已经形成从记录/创建、提醒响应到日程变更的完整用户主线，P1、P2、P3 的职责边界也基本清楚，可以指导快速原型。不过原文仍保留四项待决策内容；如果不先确定，时长追问、暂停、临时记录和撤销无法形成唯一可验收行为。

本原型采用以下暂定决策：

| 待决策项 | 原型决定 | 原因 |
|---|---|---|
| 暂停是否进入 MVP | 进入 | Proposal 验收项已明确要求暂停和恢复 |
| 撤销窗口 | 10 分钟 | 足以修正刚发生的语音误操作，又不会无限保留复杂逆操作 |
| 时间段默认时长 | 不设默认，必须追问结束时间或时长 | 避免错误默认值制造虚假冲突或漏报冲突 |
| 停车位置是否独立建模 | 作为 24 小时临时记录，分类可标记为 parking | 保持交互统一，不在 MVP 增加专用实体 |

这些决定用于原型实现，不等同于替代产品负责人对 Proposal 的最终确认。

## 验收覆盖

| Proposal 能力 | 原型设计与验证 |
|---|---|
| 单次及日/周/月创建 | `calendar_create` 与周期测试 |
| 时间段必填结束/时长 | 服务端校验，不依赖 Agent 自觉 |
| 点/段冲突与确认后并存 | 区间重叠算法、确认令牌、拒绝不落库 |
| 今天/日期/周/月/年查询 | `calendar_query` 使用明确半开时间范围；Agent 负责自然语言边界 |
| 非敏感临时记录 | 24 小时 `short_notes`，敏感词服务端拒绝 |
| 主提醒、15 分钟弱提醒 | 时间段日程默认创建；可明确关闭；独立持久化且无操作按钮，不替代主提醒 |
| 语音与 IM 同时送达 | 先持久化并发布 IM，再异步播放 TTS |
| 多项提醒按顺序播报 | 按触发时间排序后合并为一次 TTS，防止连续音频丢失 |
| 关闭/推迟不改日程 | 独立提醒状态机和回归测试 |
| 最多三次推迟 | 第三次再次到期只留 IM，不再主动播报 |
| 单次日程字段修改 | `calendar_modify` 的 `this_occurrence` |
| 周期三种范围 | 覆盖仅本次、本次及以后分割系列、整个系列 |
| 跳过、暂停/恢复、终止、删除 | 独立 MCP 工具与 SQLite 状态 |
| 高风险确认 | 跳过、单次取消、终止、删除使用参数绑定的确认令牌 |
| 改期冲突 | 与创建共用区间语义，确认前不保存 |
| 语音与 IM 结果回执 | 所有变更写入 `Receipt` 并通过 SSE 推送本地 IM |
| 撤销近期操作 | 事件、例外实例和提醒快照，10 分钟内恢复 |

## 仍需人工验证的产品问题

1. 24 小时是否适合所有临时记录，还是停车位置应在用户取车后才过期。
2. “本次及以后”分割成两个系列后，未来是否需要在查询回执中显式显示系列已分割。
3. 第三次推迟后只保留 IM 是否足够，还是应把提醒自动关闭并给出明确状态。
4. 当前将“有明确开始时间的日程”落为时间段日程默认弱提醒；点提醒只在用户明确要求时开启。仍需验证用户是否把某些无结束时间的事项也理解为“有明确开始时间”。
5. 生产环境的主动播报送达重试、设备离线和跨设备去重不在本次快速原型范围内。
