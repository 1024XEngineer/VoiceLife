# ADR 0001：采用组件化模块单体与 Ports/Adapters

- 状态：Accepted
- 日期：2026-08-03
- 决策人：VoiceLife 团队
- 关联：Issue #91、MS3

## 决策

设备侧采用 ESP-IDF 组件化模块单体，内部按 Domain、Application、Adapter 和 Runtime 分层；业务核心使用纯 C++，依赖只能从外向内。重大边界由代码中的 `idf_component_register` 依赖和主机测试共同约束。

## 原因

PCB MVP 已证明业务路径可行，但其中心化 `Application`、大量条件编译和文件状态不适合继续扩展。VoiceLife 接下来要迁移小智音频、XRobot、持久化和多个 IM 平台，最需要的是可替换边界和开发机可测试性，而不是微服务部署能力。

## 具体边界

- Schedule 保存“用户安排了什么”。
- TimingTask 保存“何时触发哪一次”。
- Application 负责跨领域用例和原子性。
- MCP 负责 Schema、路由和映射，不持有业务状态。
- Voice 负责编排会话、音频与工具调用，不执行日程业务。
- IM 负责通知投递和动作通道，不成为本地业务事实源。
- Runtime 是唯一组装入口，不写业务规则。

## 后果

收益：核心能在无硬件环境测试；替换外部平台只影响 Adapter；ESP-IDF 组件依赖可以阻止反向引用；小智能力可以逐段迁移。

成本：需要维护 Port、映射和契约测试；简单功能会比直接在 `Application` 里写代码多一层；跨领域事务必须明确设计，不能靠调用顺序碰运气。

## 未采用

- 微服务：设备侧没有独立部署、扩缩容和网络隔离收益。
- 通用 DDD 框架：当前领域规模不需要 Aggregate 基类、事件总线基类或泛型 Repository。
- 完整复制小智：会把多板矩阵、显示资源和全局状态一起带入，继续锁定旧边界。
