# 工程文档入库与 Issue 归档规范

结论先说：主仓库只保留当前版本必须阅读、能随代码长期维护、并且已经经过验证的文档；原始研究、过程记录和一次性证据统一放在 Issue 或 PR Review 中。提交代码 PR 前，作者必须把研究结论提炼成稳定文档，或者明确说明本次不需要内化。

这条规则的目的不是减少记录，而是把不同寿命的内容放在合适的位置。仓库回答“现在系统怎么工作”，Issue 回答“为什么这样决定、当时看过什么”，PR 回答“这次改了什么以及是否值得合并”。

## 1. 判断顺序

拿到一份新文档时，按下面顺序判断：

1. 用户、部署者或贡献者在当前版本运行系统时是否必须阅读？是，则进入主仓库。
2. 文档是否描述稳定的接口、架构边界、数据模型、配置契约或可重复的操作步骤？是，则进入主仓库。
3. 文档是否主要记录查资料、比较方案、临时实验或评审过程？是，则放在 Issue 或 PR Review，不直接入库。
4. 文档是否包含凭据、个人数据、设备备份、完整串口日志或其他不应传播的内容？不进入 GitHub；需要时只保留脱敏后的结论和校验值。

如果同时满足第二和第三项，先把原文放入 Issue，再从中提炼一份短小的稳定文档。不要把研究笔记原样改名后提交到 `docs/`。

## 2. 应进入主仓库

以下内容属于产品或工程当前状态的一部分，应与代码一起 Review 和维护：

- README、快速开始、部署、烧录、恢复、排障和用户使用文档；
- 当前版本必须遵守的架构边界、公共接口契约、数据模型、迁移说明和稳定 ADR；
- 影响构建、测试或运行的配置、Profile、schema、fixture、迁移脚本和 manifest；
- 可重复执行的硬件操作手册，包含必要的前置条件、验证指标、回退步骤和已知限制；
- 公共 API 文档、代码注释，以及能帮助维护者正确修改代码的短说明。

入库文档必须满足三个条件：范围清楚、事实能由代码或测试核对、失败时有明确处理办法。只写愿景、技术名词或“未来可以扩展”的文档不算稳定工程文档。

## 3. 不直接进入主仓库

下面这些内容保留在 Issue、PR Review 或受控的外部存储中，不作为主仓库文件：

- 原始资料摘录、逐来源研究文件、来源 CSV 和未经整理的对比矩阵；
- `research/` 日志、`plan`、`delta`、`diff`、`refresh target` 和临时方案草稿；
- 一次性实验记录、完整串口日志、设备备份、临时截图和只对某次测试有意义的输出；
- 只用于解释某个 PR 的中间材料、评审意见、未采纳方案和反复修改的草稿；
- AI 原始分析、Prompt 产物和未经人工核对的总结；
- 凭据、令牌、Wi-Fi 信息、用户隐私、未脱敏设备数据和任何可恢复秘密。

“放在 Issue”不等于可以把秘密贴到 Issue。敏感材料应留在项目允许的受控位置，Issue 只记录脱敏后的事实、哈希、范围和追溯入口。

## 4. 研究结论如何内化

研究资料有长期价值时，按下面的路径处理：

1. 先在 Issue 中保存问题、范围、来源、原始材料和不确定性，并写清哪些内容暂时不代表实现完成。
2. 把研究结论拆成“事实、决定、适用范围、未解决风险”四类，删除与当前版本无关的背景摘录。
3. 用代码、主机测试、构建、真机验证或可复现脚本核对结论；没有验证的内容只能标为假设或待验证项。
4. 将已经稳定的部分改写成短文，放到合适的 `docs/architecture/`、`docs/engineering/` 或用户文档路径，并保留来源 Issue 或外部来源链接。
5. 代码 PR 只提交实现所需的最小稳定文档；原始研究继续留在 Issue，不复制回仓库。
6. 后续事实发生变化时，新建变更 Issue 或 ADR/文档 PR，不覆盖已经作为历史依据的旧记录。

稳定文档不是研究报告的压缩版。它应该直接告诉读者当前约束、验证边界和下一步动作；如果读者仍需要逐篇阅读来源才能执行，说明提炼还没有完成。

## 5. Issue、PR 与 Review 规则

- 研究归档 Issue 负责保存原文、来源和过程证据；必要时在正文或评论中提供文件清单、版本号和历史链接。
- 研究型或阶段性 PR 使用 `Refs #Issue`，保持 Draft 或按实际完成度设置生命周期，不使用 `Fixes` 伪造完成关系。
- 只有满足目标 Issue 全部验收条件的最终实现 PR 才使用 `Fixes #Issue` 或 `Closes #Issue`。
- 堆叠 PR 不重复携带同一研究目录。研究资料迁移后，各 PR 的正文要写明统一归档 Issue。
- 设计、研究和中间验证材料必须在人工 Review 中说明结论、证据和剩余风险；AI Review 不能替代作者或人工 Reviewer 的判断。
- 清理研究文件只改变未合并分支的最终文件树，不删除 Issue、PR 或历史 commit；清理提交应使用清楚的迁移说明，保证可以回溯。

## 6. 提交前检查

作者在提交 PR 前逐项确认：

- 文件是否面向当前版本的用户或维护者，而不是只面向本次调研过程；
- 结论是否能由代码、测试或明确的实验结果核对；
- 是否把原始来源、delta、临时日志或一次性证据误放进了 `docs/` 或 `research/`；
- 是否删除凭据、隐私、设备备份和完整日志，只保留必要的脱敏结果；
- 是否在 Issue 中记录了原始研究归档位置，并在 PR 中使用正确的 `Refs` 或 `Fixes` 语义；
- `git diff --check`、文档链接检查和与本次变更相关的测试是否通过。

## 7. VoiceLife 当前执行

语音模块的原始研究资料统一归档在 Issue [#150](https://github.com/1024XEngineer/VoiceLife/issues/150)。因此，PR #108、#110、#112、#114 保留语音架构、迁移、硬件验证、代码、测试和 Profile 配置，移出 `research/voice-module-portability-20260804/`，并在 PR 正文中使用 `Refs #150`。原始研究文件仍可从 Issue 评论、清理前的 PR 头提交和 Git 历史追溯。

这份规范本身也遵循同一流程：通过独立 PR Review，合并后作为项目当前的文档放置规则；后续规则变化应通过新的 Issue 和文档 PR 记录。
