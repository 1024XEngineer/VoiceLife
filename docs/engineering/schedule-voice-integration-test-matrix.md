# 语音日程联调测试矩阵

结论：本轮实板联调按“语音输入、日程语义、提醒执行、屏幕状态”四条链路同时验收。当前版本只能承诺固定 UTC+8 下的有限周期规则；遇到其余日历语义，助手必须说明限制或追问，不能猜测后保存。

执行动作：先完成启动和模型链路门槛，再按本矩阵跑完单轮、连续多轮和到时提醒。每个失败归属为语音/状态/显示或日程领域，并记录可复现输入、MCP 调用、串口明文、屏幕观察和修正后的回归结果。

关联操作基线：[百炼与 SparkBot 语音验证](bailian-sparkbot-voice-validation.md)。原始串口日志和含凭据的请求不得提交；可保留已核验的指标、错误码和脱敏后的会话编号。

## 1. 当前承诺与边界

边界依据已单独固化在[语音日程边界调研与本期取舍](schedule-voice-industry-boundaries.md)。本矩阵只保留可执行的验收项；遇到行业常见但当前未开放的能力，测试目标是“明确拒绝或澄清且不写入”，不是要求本期补齐全部日历标准。

| 语义 | 当前承诺 | 语音层的正确行为 |
| --- | --- | --- |
| 一次性日程 | 固定 UTC+8 的开始/结束时间、地点、备注、冲突检查 | 缺日期或时间时追问；冲突时说明冲突并等待确认，不默认覆盖 |
| 周期规则 | 每日、指定周几、指定每月日期、每月最后一天、每年某月某日；可设间隔和结束日期 | 复述规则、首个发生时间和结束范围后再确认成功；“第 N 个周几/最后一个工作日”明确不支持 |
| 单次例外 | 跳过或修改一个尚未物化的周期实例 | 必须定位到具体日期；“这次”不唯一时追问 |
| 查询 | 已落库日程和查询窗口内的周期发生时间 | 查询日期必须进入日程层的窗口展开，不能只从“三条近期发生”过滤；结果必须先应用 skip/modify 例外 |
| 时区 | 仅 UTC+8 | 用户说异地/夏令时/其他时区时说明当前限制，不能换算后静默保存 |

以下属于标准日历产品常见语义，但本版不支持：发生次数上限、每月第 N 个或最后一个工作日、任意 RRULE 字段、按“此后所有”修改系列、IANA 时区和夏令时。对于“每月最后一个工作日提醒我”或“去纽约后按当地时间提醒”，模型应澄清为可表达的固定日期规则，或明确告知暂不支持；不得将其伪装为每月最后一天或 UTC+8 的普通规则。

代码审计已确认两个查询风险，尚未把它们当作“语音模型偶发错误”：

- `ScheduleRuleService::query_schedule_rules` 当前只展开每条规则最近三次发生时间。`schedule.query` 再按用户日期过滤时，查询几个月后的日期可能错误返回空结果。
- 查询返回的 `upcoming_occurrences` 没有先应用 skip/modify 例外，可能把已经跳过或已改时间的原始发生时间展示给用户。

这两项必须由日程层修正，并用远期查询、跳过一次、修改一次三组回归用例锁定；语音层只能如实播报业务结果，不能增加“远期查询再问一次”之类的分支掩盖问题。

这个边界来自 iCalendar 的 RRULE/RECURRENCE-ID 语义、Google 对单次及“此后”系列修改的区分，以及 Microsoft 对 recurrence pattern 和 range 的拆分：

- [RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.txt)：规则、例外、无效日期及本地时间语义。
- [Google Calendar recurring events](https://developers.google.com/calendar/api/guides/recurringevents)：单次、整组与后续系列的操作范围。
- [Microsoft recurrence pattern](https://learn.microsoft.com/en-us/graph/api/resources/recurrencepattern) 与 [range](https://learn.microsoft.com/en-us/graph/api/resources/recurrencerange)：模式和生效范围是独立概念。

## 2. 进入实板压测的门槛

1. 冷启动连续 10 次：每次均出现 `NVS_READY=1`、`DISPLAY_READY=1`、`MCP_TOOLS_READY`、`SCHEDULE_REMINDER_READY=1`，没有 panic、重启或栈溢出。
2. Linx 已连通；百炼 TTS -> STT 严格回环可识别原文本，分别保存首包、总耗时、HTTP/会话结果和音频字节数。
3. 屏幕可见启动、聆听、思考、播报、错误和提醒状态；状态文字固定一行，长内容在左右安全边距内横向循环滚动，不覆盖表情，不截断 UTF-8 字符。
4. 采样前清空本次测试数据，设备时钟和日期已核对为 UTC+8；测试结束导出日程、规则、例外和操作记录以核对事实。

门槛不通过时停止语义压测，先修启动、网络或音频根因。网络瞬断可单列为环境失败，但同一现象重现两次即按产品缺陷追踪。

## 3. 语音日程测试矩阵

每格至少走一次真实音频：百炼 TTS 生成测试话术，经串口注入实板，由 Linx 识别、调用 MCP、播报回应。高风险格在连续会话中重复三次。

| 组别 | 覆盖输入与变体 | 期望业务结果 | 同时验收的语音/屏幕结果 |
| --- | --- | --- | --- |
| 创建 | 精确一次性日程；地点、备注；今天/明天/本周五；跨午休和重叠事件 | 时间解析正确；冲突不丢失既有日程 | ASR 明文、MCP 参数、确认播报一致；思考到播报无卡死 |
| 信息不全 | “明天提醒我开会”“下午开会”“下周安排复盘” | 未写入；一次只追问最小缺失字段 | 屏幕为澄清而非成功；补答后只创建一条 |
| 指代与歧义 | “改成三点”“取消那个会”“把下周的会挪一下”且候选不少于两个 | 提供候选或追问唯一标识；不得误改/误删 | 多轮上下文保留到确认或取消；显示的对象与播报一致 |
| 查询 | 今天、明天、本周、指定远期日期；关键词；没有日程 | 返回请求窗口的完整发生集合，含远期周期规则和例外后的结果 | 无结果清晰播报；屏幕不残留上一条查询文本 |
| 基础周期 | 每天；工作日；周一和周三；每两周；每月 15 日；每月最后一天；每年生日；带结束日 | 首次和后续发生时间正确，间隔/范围正确 | 复述不省略频率、星期、结束条件；查询可见规则 |
| 无效日期 | 每月 31 日跨 30 天月/二月；每年 2 月 29 日跨平年 | 无效月份跳过且不被算作发生次数；不得偷偷移到月末 | 回应说明规则保持原意；查询与生成一致 |
| 周期例外 | 跳过下周三；仅将 9 月 3 日改到 10 点；已物化实例再修改 | 例外只影响指定一次；已物化实例走实例更新 | MCP 使用 `rule_id + original_start_time` 或 `schedule_id`；之后查询和提醒一致 |
| 范围与长期 | 结束日期在首次前/同日/多年后；远期查询；取消整条规则 | 合法范围正确；取消后无未来提醒 | 不把规则取消误报为仅取消一次；操作记录可追溯 |
| 不支持规则 | 第三个周二、最后一个工作日、10 次后停止、从下月起都改为 10 点、IANA 时区和夏令时 | 不写入或先转成用户明确确认的可表达规则 | 清晰说明限制和替代；无“成功创建”假回应 |
| 时区与时钟 | 北京/纽约/夏令时描述；设备时间错位；重启后 | 非 UTC+8 语义拒绝或澄清；重启后只恢复应有提醒 | 错误可理解且状态恢复；不会重复播报或漏播 |
| 提醒 | 1-3 分钟后的一次性提醒；周期下一次；提醒时正在聆听、思考、播报、网络重连 | 只触发一次；取消/更新同步撤销旧任务；下一周期正确生成 | 提醒播报不与对话 TTS 重叠；可中断或排队的行为一致，屏幕优先显示提醒来源 |

## 4. 长对话压测脚本

每轮包含 12-20 个有依赖的真实语句，至少执行 5 轮，共不少于 80 个语音回合。每轮穿插闲聊、停顿、纠正和打断，避免只测“命令词一次成功”。

1. 创建“明天上午十点产品评审”，补地点；追问“明天还有什么”；再创建冲突会议，拒绝覆盖；将第一场改为十点半；查询确认。
2. 创建每周一和周三的站会，跳过下周三，仅改下下周一；询问指定远期日期的安排；取消整条系列后确认提醒已撤销。
3. 创建每月 31 日和每年 2 月 29 日；跨过无效月份/平年后查询；分别输入“最后一个工作日”和“十次后停止”，确认系统不静默降级。
4. 创建 1-3 分钟后的提醒；在聆听、思考和 TTS 过程中分别触发；用“停一下”“继续”“取消提醒”观察抢占、恢复和最终日程事实。
5. 连续创建多个名称相近的会议；用“改下午那个”“取消刚才的”测试澄清；在最后一条日程确认后重启设备并再次查询、等待提醒。

## 5. 每回合必须记录的证据

| 层 | 必须记录 |
| --- | --- |
| 音频与模型 | 原始文本、TTS request_id/首包/字节数、STT request_id/结果、注入与最终回应耗时 |
| 状态机 | 唤醒、聆听、识别完成、工具调用、TTS、空闲、错误、恢复的顺序和时间戳；是否出现非法跳转 |
| MCP 与日程 | 工具名、参数、结果、规则/实例/例外 ID、冲突、提醒任务 ID、重启前后数据库快照 |
| 屏幕 | 每次状态的截图或人工观察：单行横向滚动、表情可见、文本准确、没有残影或覆盖 |
| 资源与恢复 | 可用堆/PSRAM、任务栈高水位、I2S 与队列指标、网络断开重连、panic/重启计数 |

## 6. 缺陷分流与通过条件

语音、状态机、TTS/STT、串口协议、显示、队列、音频抢占和资源泄漏归“语音交互缺陷”；规则展开、冲突、例外、查询窗口、持久化和提醒排程归“日程领域缺陷”。跨层问题先以用户可见错误作为主归属，并列出阻塞层，不为某句话添加特判。

阶段通过条件：所有矩阵格已有结果；支持语义的日程事实、播报和显示一致；不支持语义没有写入；80+ 回合中不存在 panic、非法状态跳转、重复/遗漏提醒或错误对象修改。瞬时网络失败应有可见恢复或明确失败提示，并保留证据，不以一次偶发波动掩盖可重复故障。
