# Fenno 辅助 PR Review 工作流

结论：VoiceLife 把 Fenno 当作 PR 的 AI 预审助手，使用 `/review` 在人工 Review 前检查 diff；Fenno 的评论只能提供线索，不能替代作者、Reviewer、CI、实板验收或合并权限。

执行动作：从本规范生效起，作者在准备进入人工 Review 的 PR 上运行一次脱敏后的 `/review`，逐条判断结果并把采纳项、误报和未完成项留在 PR 记录中；涉及改代码、重构或关闭对象时，必须回到人工确认和既有 Issue/PR 流程。

## 1. 适用范围

本规范适用于 VoiceLife 的固件、显示、音频、语音状态机、日程、IM、测试、CI 和工程文档 PR。它补充而不改变既有链路：

```text
Proposal -> Design(Issue) -> Coding(PR) -> Review -> Merge
```

Fenno 只插入 `Coding(PR)` 与人工 `Review` 之间的预审步骤。它不改变分支保护、Milestone、Issue 关联、测试门禁或人工批准要求。

## 2. Fenno 能做什么

Fenno 官方中文文档说明它通过 GitHub App 集成到 Issue 和 PR 的评论中。命令的边界如下：

| 调用 | 位置 | 在 VoiceLife 中的用途 | 默认权限 |
| --- | --- | --- | --- |
| `@fennoai` | Issue / PR | 询问设计、解释代码、讨论风险；这是对话模式 | 只读，不写代码、不提 PR |
| `/plan` | Issue | 在编码前请求受影响文件、迁移策略和风险清单 | 只读，不作为设计批准 |
| `/review` | PR | 审查 diff 中的 Bug、安全、性能和代码质量问题 | 只读预审，返回行内评论 |
| `/compact` | Issue / PR | 评论过多时汇总已决事项、待解决项和下一步 | 只整理上下文，不改变代码 |
| `/code` | Issue / PR | 让 Fenno 编写代码并提交 PR | 本团队默认不在现有 Review 中使用 |
| `/simplify` | PR | 重写并精简 PR 分支代码 | 本团队默认不在现有 Review 中使用 |
| `/close` | Issue / PR | 关闭对象 | 不授权给 Fenno 自动执行 |

`/code` 和 `/simplify` 不是普通预审的“修复按钮”。如果确实要让 AI 改代码，应先建立或确认对应 Issue，明确授权范围，检查生成 diff，并重新运行全部相关门禁。

## 3. 标准流程

### 3.1 作者发起预审前

作者先完成下面的人工准备：

- PR 标题遵循仓库约定，关联一个明确 Issue，并说明 Draft/Ready 状态。
- 运行与改动匹配的主机测试、静态检查、构建或实板测试；不要让 Fenno 代替基础验证。
- 检查 diff 是否包含无关文件、构建产物、串口原始日志、音频文件或密钥。
- 对需要发送的上下文做脱敏，确认 PR 评论不会暴露凭据、个人数据或设备唯一标识。
- 在 PR 描述写清本次改动、已知限制和需要 Reviewer 特别关注的风险。

没有可审的 diff 时，不调用 `/review`。设计仍在讨论时，优先在 Issue 使用 `/plan` 或 `@fennoai`，不要把设计问题伪装成代码 Review。

### 3.2 调用 `/review`

在 PR 评论中发送 `/review`。如果 PR 风险集中在某个模块，追加明确范围：

```text
/review

请按以下顺序审查本 PR：
1. 可能导致现有行为回归的逻辑错误；
2. 内存、线程、资源生命周期和错误路径；
3. 安全、隐私和日志泄露；
4. 测试是否覆盖本 PR 的验收标准。

请只基于当前 diff、仓库现有代码和 PR 描述给出可验证的问题，按 Critical / High / Medium / Low 分级，说明文件、行号、触发条件和修复建议。无法确认的内容标记为“需人工验证”，不要假设硬件、网络或真实语音结果。
```

聚焦调用示例：

```text
/review 重点关注 LVGL 对象是否都在半高 viewport 和 safe inset 内，是否存在跨线程更新、父容器裁剪失效或长文本滚动越界。
```

Fenno 返回行内评论后，作者不要一次性解决全部评论。先把每条评论放入结果表，再逐条验证。

### 3.3 处理 Fenno 评论

| 结论 | 作者动作 | PR 记录 |
| --- | --- | --- |
| 采纳 | 修改代码或测试，说明对应评论；重新运行相关门禁 | 回复评论并在 PR Verification 更新结果 |
| 解释并保留 | 用代码、测试或设计 Issue 说明为什么不改 | 回复理由和证据，必要时请求 Reviewer 判断 |
| 误报 / 不适用 | 指出 Fenno 使用了错误前提或超出范围 | 标记原因，不为了“清零”而改代码 |
| 需实板/真实语音验证 | 不在主机上臆测结论，安排 HIL 或人工旅程 | 写明验证负责人、证据位置和当前状态 |
| Critical / 安全疑点 | 暂停合并，先人工复现和升级 | 在 PR 顶部标明阻塞原因 |

`/compact` 只在讨论过长、需要重置上下文时使用。使用后人工检查汇总是否遗漏了原始 Review 意见；不得把机器人汇总当成批准。

### 3.4 人工 Review 与合并

Reviewer 仍需独立阅读 diff。合并前必须满足：

- Fenno 预审评论已逐条分类，没有未解释的 High/Critical 项。
- 相关主机测试、构建、LVGL 渲染测试、实板视觉验收和真实语音联动均按 PR 范围完成，或在 PR 中明确记录未完成项和风险。
- 人工 Reviewer 已确认设计 Issue、模块边界、回退方式和不做范围。
- CI、分支保护和必要的人工批准全部通过。

Fenno 无权批准、合并、关闭 Issue 或改变 PR 生命周期。阶段性实现继续使用 Draft 和 `Refs #...`；只有人确认满足 Issue 验收标准后，才可转 Ready 并按仓库流程决定 `Fixes` 关系。

## 4. VoiceLife 专项检查清单

调用 `/review` 时，根据改动类型补充对应关注点。

### 固件、ESP-IDF、音频和语音

- 任务栈、TCB、队列、缓冲区和 PSRAM/内部 RAM 的分配是否与硬件约束一致。
- 启停、断连、重连、异常和析构路径是否会重复释放、死锁、丢通知或遗留旧任务。
- `DisplaySnapshot` 的 generation/revision、phase、mood、status_text 和 content_text 是否仍与语音状态机同源。
- 是否误改音频格式、AEC、语音协议、配网或其他板型行为。
- 错误恢复后能否重新唤醒，是否把一次错误永久留在显示或音频状态中。

### SparkBot 显示和 LVGL

- ST7789/LVGL 控制器逻辑分辨率、旋转、镜像、offset 和默认面板初始化是否保持不变。
- SparkBot 产品 viewport、左右 safe inset、状态槽、表情/动画槽和正文槽是否越界或重叠。
- LVGL 对象是否只在显示任务线程更新，父容器裁剪和 label 长文本模式是否符合契约。
- 中文断句、英文/数字串、两行限制、横向滚动、打断复位是否有测试和实板证据。
- 播报状态是否保留表情且正文不遮挡；待机屏保退出条件是否覆盖新快照、提醒和错误。
- 资产 manifest、GIF 尺寸、字体 fallback 和资源失败回退是否可验证。

### 日程、IM 和服务端

- 时区、边界、幂等、重试、重复提醒和状态收口是否改变既有契约。
- IM 投递是否有平台受理回执、失败重试和去重依据。
- 日程摘要、提醒、打断和恢复是否回到同一个语音/显示状态源。
- 日志和错误返回是否泄露 token、绑定信息、用户日程或设备标识。

### 测试和文档

- 测试是否真的覆盖 PR 验收标准，而非只增加快照或字符串断言。
- 主机契约、LVGL 渲染、实板视觉、真实语音联动是否被清楚区分。
- 测试失败是否属于本 PR，还是既有环境/外部依赖问题；不要让 Fenno 替作者做归因。
- 文档是否写清不做范围、风险、回退和下一步，而不是只列功能。

## 5. 数据与安全边界

发送给 Fenno 前，作者必须删除或替换：

- Wi-Fi 密码、API Key、OAuth Token、Cookie、私钥、签名材料和任何 `.env` 内容。
- MAC、序列号、绑定码、设备路径、个人账号、手机号、地址和未公开服务 URL。
- 原始麦克风音频、完整用户对话、未脱敏串口日志和包含认证响应的网络抓包。

可以保留帮助 Review 的最小上下文，例如脱敏后的错误码、状态名、时间相对顺序、代码片段和测试摘要。需要硬件或真实语音结论时，只在 PR 放置脱敏证据路径和摘要，不把原始材料粘贴到评论。

仓库管理员需单独确认 GitHub App 的安装范围、组织权限、数据保留政策和退出方式；本规范不默认已经完成这些审计，也不在仓库提交 Fenno 凭据或 `.fennoai.yml`。

## 6. 记录模板

作者可在 PR 描述或 Verification 区域追加：

```markdown
### Fenno 预审

- 调用时间：2026-08-20
- 命令：`/review`（范围：显示 viewport、LVGL 线程和长文本滚动）
- 结果：`N` 条评论；采纳 `__`，解释并保留 `__`，误报 `__`，需实板验证 `__`
- 采纳项：`<提交或评论链接>`
- 未完成/阻塞：`<人工验证或外部依赖>`
- 结论：Fenno 预审不替代人工 Review；CI/HIL/真实语音结果见下方清单。
```

记录应引用评论或提交链接，不复制整段可能含敏感信息的机器人输出。PR 描述只保留能帮助后续 Reviewer 判断的摘要。

## 7. 失败与升级

出现以下任一情况，停止依赖 Fenno 结论并转人工处理：

- Fenno 无响应、上下文明显不完整、引用不存在的文件/接口或与当前 diff 矛盾。
- 评论涉及安全漏洞、隐私、数据删除、硬件损坏、真实语音体验或合规判断，且无法由主机测试验证。
- Fenno 建议修改范围超出 PR 所属 Issue，或要求绕过测试、分支保护、Review 或实板验收。
- 机器人评论与人工 Reviewer、CI 或实板证据冲突。

升级时在 PR 写明：冲突点、已核对的代码/测试/证据、最终人工决定和是否需要新 Issue。不要通过 `/close` 清理争议，也不要通过 `/simplify` 掩盖未解决的行为问题。
