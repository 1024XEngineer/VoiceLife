# 日程与语音联动测试设计

结论：日程联调不能只验证“标准句子能创建”。当前验收必须覆盖自然人信息不全、表达含糊、修正和冲突，以及日程到点后提醒语音与屏幕状态的完整链路。本计划是下一轮百炼实板测试的入口；没有按矩阵执行并保留证据，不把日程模块称为“完整通过”。

适用范围：`schedule.*` MCP 工具、周期规则、操作记录、`ScheduleReminderService`、Timing Runtime、Linx TTS、VoiceSession 状态机、SparkBot 字幕和音频队列。输入语音统一由阿里云百炼 TTS 生成，设备端实际走 Linx STT/TTS；串口保存明文应用证据，但密钥、原始私密音频和完整 Authorization 信息不得进入 Git。

## 1. 统一验收门禁

每个用例都记录输入原文、百炼 TTS request_id、板端 `stt_text_received`、MCP 工具名与结果、TTS 句子文本、串口状态、屏幕快照和 `AUDIO_STATS`。通过条件如下：

- 语义门禁：信息完整时工具参数准确；信息不足或歧义时必须澄清，不得猜测并写入日程；用户补充后只能产生一次正确写入。
- 状态门禁：普通回合必须按 `capture_started -> speech_started -> capture_stopped -> stt_text_received -> tts_started -> tts_first_audio -> tts_stopped` 运行，且每回合覆盖 phase `3/4/5/6`。
- 显示门禁：状态文案与 phase 一致；内容区只占一行，长内容在左右安全边距内横向循环滚动，不覆盖表情；每次滚动快照包含 generation、revision、viewport 和 `overflow_width`。
- 音频门禁：`in_drop`、`in_pool_fail`、`out_reject`、`short_write`、`in_i2s_err`、`out_i2s_err`、串口 PCM reject 和交互队列丢弃均为零。设备提前端点时，夹具必须停止发送并报告 `input_endpoint_truncated`，不能用拒绝噪声掩盖问题。
- 定时门禁：注册、到点、播报、完成/生成下一实例和取消均有可关联的 `schedule_id -> task_id` 证据；提醒播报必须真实进入 TTS 播放，屏幕显示“提醒/说话中”，播放完成后恢复可用待机，不得静默丢失或重复触发。

云端 ASR 只做文字保真门禁，不把“十分钟/10分钟”、标点、礼貌前缀缺失等模型表达差异伪装成设备或日程成功。语义正确但文字不一致必须单列为模型保真失败。

## 2. 测试数据设计

用例使用当前日期附近的未来日期；定时触发用例使用运行时计算的 60--120 秒后时间，避免固定日期过期。每个场景先清空内存仓储或使用唯一事件名，重启后不得假设内存日程仍存在。

### 2.1 正常人与信息完整度

| 编号 | 口语场景 | 预期行为 |
| --- | --- | --- |
| N1 | “明天下午三点提醒我开会” | 缺事件标题时澄清，不创建 |
| N2 | “安排一下产品评审” | 缺时间时澄清，不创建 |
| N3 | “下周一”/“月底”/“过一会儿” | 相对时间可解析时确认绝对时间；不可解析时澄清 |
| N4 | “下午三点”跨 12 点、“八点半”“三刻” | 转换准确并在 TTS 中复述绝对时间 |
| N5 | “周三、周五都要”/“隔周”/“每月最后一天” | 映射 weekly/monthly 规则；不支持的表达要说明限制 |
| N6 | 先说“十点”，随后补充“不是上午，是晚上” | 只保留修正后的值，不能留下两个日程 |
| N7 | 省略主语、口语停顿、重复词、同音字、中文/阿拉伯数字混说 | 语义正确；ASR 差异单独记录 |
| N8 | 地点、备注、持续时间未提供 | 可选字段保持为空，不能编造结束时间或地点 |
| N9 | 用户说“算了/不要了/别创建”在工具调用前后 | 未调用时不写入；已调用时执行取消并说明结果 |

### 2.2 一次性日程与操作记录

覆盖创建、按日期/关键词/状态查询、指代修改（“刚才那条”）、改时间/标题/地点/备注/结束时间、删除、重复删除、删除后查询、`schedule.operation_query` 的创建/修改/删除记录。验证过去时间、当天时间、结束早于开始、空标题、超长字段、非法日期、无目标指代和同名多条日程时都澄清或返回可理解错误。

### 2.3 周期规则和单次例外

覆盖每日、每周多选星期、每隔 N 周、每月指定日、每月最后一天、每年、结束日期、发生次数；查询未来 occurrence；修改整条规则；只修改某一次 occurrence；跳过某一次；取消整条规则；取消后重建。验证规则起始日不匹配星期、月底不存在日期、已发生实例、规则冲突和规则生成失败重试。

### 2.4 冲突与并发语义

创建重叠点、区间包含、部分重叠、相邻不冲突、周期实例冲突；修改导致冲突；明确“仍要创建/忽略冲突”后才允许 `ignore_conflict=true`。连续快速创建两条同一时间日程，必须不重复写入、冲突结果可解释。工具失败时不得播报成功。

## 3. 定时触发专用场景

每个触发场景都使用唯一标题，并在触发前后保存连续串口日志。创建后先查询确认 active、未来 start_time 和 reminder task 已登记，再等待短窗口，不进行 30 分钟待机观察。

| 编号 | 场景 | 关键验收 |
| --- | --- | --- |
| T1 | 创建 60--120 秒后的一次性日程 | 到点只触发一次；日志含 `task_id`、提醒文本、TTS start/first audio/stop；日程变 completed |
| T2 | 创建后在到点前删除 | timing cancel 被接收；到点窗口无提醒 TTS、无状态 6 |
| T3 | 到点前修改时间 | 旧 task 被取消，新 task 到新时间触发一次；旧时间不播报 |
| T4 | 周期日程首个实例临近触发 | 当前实例完成，下一实例生成并注册；不重复播报 |
| T5 | 到点时设备正在聆听 | 不能静默丢提醒或破坏用户输入；必须有明确抢占策略（排队或受控打断），记录 generation 与原因 |
| T6 | 到点时设备正在播放普通回答 | 普通回答与提醒不能交叉播放；必须按策略排队/打断，旧 PCM 不穿透 |
| T7 | 网络短暂断开后到点 | 提醒失败必须有失败证据和可恢复策略，不能宣称已播报；恢复后不重复触发已完成任务 |
| T8 | 重启后恢复未来日程 | `Start()` 重新登记 task；到点仍只播报一次；已取消/已完成的不恢复 |

提醒回合还要复用普通语音门禁：状态显示固定一行、长标题横向滚动、音频无 reject/short write，播报结束恢复可唤醒或可接受下一轮的状态。若 `VoiceSession::Speak` 只接受 `kReady`，T5/T6 必须先验证并记录这是架构阻塞，而不是把失败归咎于网络。

## 4. 执行顺序与证据

1. 先跑主机 80/80 CTest、Profile 校验和 ESP-IDF 构建；确认固件 commit、模型和板卡。
2. 用百炼服务做短语义预检，确认 TTS 非空、request_id 存在；不以云端文字相等代替实板验证。
3. 按 N1--N9 逐项执行，先完成澄清类，再执行写入类，避免前一条脏数据污染后一条。
4. 执行一次性/周期/冲突矩阵，再执行 T1--T8。每个场景失败立即保留日志并停止该场景，不进行无意义长时监控。
5. 结果分为“语音模块问题”（端点、状态、字幕、TTS、音频、队列、定时播报接入）和“日程模块问题”（解析意图、参数、冲突、规则、仓储、task 生命周期）。修复必须针对通用机制，并为根因增加主机回归或实板回归。

## 6. 行业规则调查与本项目采用的语义边界

本轮参考了 Google Calendar recurring events、Microsoft Graph recurrence pattern 和 RFC 5545 RRULE 的公开规则说明。它们共同强调三件事：周期规则必须有明确的锚点和时区；`COUNT`/`UNTIL` 是结束边界；月末、闰日和按星期序号的规则不能用“每隔固定天数”代替。Google 的 recurring event 还将规则定义与单次 instance 分开，允许修改或取消单次 occurrence；RFC 5545 允许 `BYMONTHDAY`、`BYDAY`、`COUNT`、`UNTIL` 等约束，但没有把“2 月 31 日”悄悄改成 2 月最后一天的通用约定。

本项目当前领域模型固定为东八区 civil date/time，周期类型为 daily / weekly / monthly / yearly；monthly 只有 `specific_day` 和 `last_day`，yearly 使用 `month_of_year + day_of_month`。因此测试必须把产品语义说清楚：

- 每月指定日遇到不存在的日期（例如每月 31 日的 2 月）应跳过该月，不能自动改成月末；每月最后一天才使用当月实际最后一天。
- 每年 2 月 29 日在非闰年应跳过该年，不能播报为 2 月 28 日；查询应明确告诉用户下一次有效日期。
- “每月最后一个工作日”“每年某月第一个周一”“每两个月”等超出当前模型的表达必须澄清能力边界，不得假装映射成相近规则。
- 用户问“某天要做什么”时，查询范围必须覆盖用户指定的 civil date，而不是只依赖从当前时间起的固定数量 occurrence。当前 `ScheduleRuleService::query_schedule_rules()` 生成 3 个未来 occurrence 的行为是待验证的架构风险：远期日期可能被过滤掉。
- 所有自然语言时间先转换为设备本地（东八区）绝对时间并在语音中复述；不能用云端时区或手机时区覆盖设备规则。

调查来源（2026-08-19 直接抓取的官方文档；本次环境未提供 WebSearch/WebFetch MCP）：

1. Google Calendar API, Recurring events: https://developers.google.com/calendar/api/concepts/events-calendars （primary）
2. Microsoft Graph, recurrencePattern: https://learn.microsoft.com/en-us/graph/api/resources/recurrencepattern?view=graph-rest-1.0 （primary）
3. IETF RFC 5545, iCalendar specification, recurrence rule grammar: https://datatracker.ietf.org/doc/html/rfc5545 （primary）

## 7. 长周期语音交互矩阵

下面每条都必须由百炼 TTS 生成输入音频，板端 Linx ASR 识别后调用真实 MCP；不能只用 JSON 直接调用工具。每条至少记录：输入原文、TTS request_id、板端 ASR 文本、工具参数、返回的 `schedules/future_occurrences/exceptions`、设备字幕和状态事件。

| 编号 | 正常人说法 | 预期工具路径与语义 | 失败归类 |
| --- | --- | --- | --- |
| L1 | “我每个月 15 号交房租，查一下下个月 15 号要做什么” | `schedule.query(start_date=下月15日,end_date=下月15日)` 必须返回该周期 occurrence；只返回未来 3 次但漏掉目标日期为日程查询缺陷 | 日程/查询架构 |
| L2 | “每个月最后一天记账，下个月最后一天有什么安排” | 返回下月真实月末；2 月、4 月等不同月长分别验证 | 日程/规则 |
| L3 | “每月 31 号盘点，二月份那次有吗” | 2 月没有该 occurrence，明确说明跳过，不改成 2 月 28 日 | 日程/规则或语音澄清 |
| L4 | “每年 9 月 1 日体检，今年这天要做什么” | 返回当年 occurrence；跨年后仍只命中目标年，不重复显示同名规则 | 日程/查询 |
| L5 | “每年 2 月 29 日提醒我续证，明年有没有” | 非闰年返回无有效 occurrence，并播报下一次有效闰年；不得生成非法日期 | 日程/规则 |
| L6 | “每两个月 10 号交报告，问今年 12 月 10 号” | 以规则 start_date 为锚点计算间隔；若目标月不是命中月，返回无安排并解释 | 日程/规则 |
| L7 | “从下个月开始每三个月一次，先查明年同一天” | 查询必须先确认锚点、时区和绝对日期；信息不全时澄清，不猜测 | 语音/意图 |
| L8 | “上个月最后一个工作日的安排是什么” | 当前模型不支持工作日序号；澄清并说明能力边界，不降级成 last_day | 产品边界/语音 |
| L9 | “每年六月第一个星期一开会” | 当前 yearly 模型不支持 BYDAY 序号；拒绝静默转换，保留用户选择空间 | 产品边界/语音 |
| L10 | “查 2027 年 2 月 28 日和 3 月 1 日的安排” | 日期窗口为半开区间 [00:00, 次日 00:00)，不漏掉午夜边界，不重复计入周期和已物化实例 | 查询/时区 |
| L11 | “我说的是北京时间晚上 11 点，不是手机显示的时间” | 设备东八区复述和 task trigger 一致；跨 UTC 日时不提前/延后一天 | 语音/时区 |
| L12 | “刚才说的每年活动，改成每月最后一天” | 先用 `schedule_rule.query` 定位唯一 rule，再 `schedule_rule.update`；只产生一个新规则版本和新提醒 | 语音/日程 |

## 8. 人类表达不精确时的对话状态矩阵

每条场景至少测试“首句不完整 -> 设备澄清 -> 用户补充 -> 确认/取消”四步，且检查中间不能产生 MCP 写入。以下表达不能被测试脚本替换成精确模板：

| 类别 | 例子 | 必须验证 |
| --- | --- | --- |
| 口头停顿/自我修正 | “每个月……嗯，最后一天，晚上八点，不对，九点” | 仅保留最后值；一次工具写入；旧时间无 task |
| 缺标题 | “明天下午三点提醒我一下” | 询问提醒内容；不创建空 event |
| 缺日期 | “每年生日提醒我” | 询问月日；不使用当前日期推断 |
| 相对词过期 | “下周一”但当前时区已跨周 | 复述具体年月日，用户否定时可回到澄清 |
| 模糊范围 | “月底”“最近”“晚点” | 询问可执行的日期/时间；不写模糊 task |
| 指代不唯一 | “把那个改到周五”有两个同名日程 | 列出候选并让用户选择；不按最近写入猜测 |
| ASR 同音/数字混说 | “两点半”“2 点半”“二点半” | 语义等价可接受；原文差异单列，不把模型文字差异算设备通过 |
| 否定/撤回 | “算了”“先别提醒”“不是这条” | 写入前取消不落库；写入后取消/恢复有明确状态 |
| 多意图 | “查一下明天安排，顺便把下午那个改晚一小时” | 先完成查询并确认目标，再执行修改；任一失败不得播报全成功 |
| 超范围请求 | “每月最后一个工作日” | 明确当前不支持，不能偷换成最后一天 |

## 9. 长周期专项验收门禁

完成 L1--L12 后，才能声称“周期查询覆盖”。通过条件：

1. 目标日期查询命中正确 occurrence，或对不存在/不支持的规则给出可理解的澄清；不能以返回规则本身代替 occurrence 命中。
2. 同一周期规则同时出现在 `future_occurrences` 和已物化 `schedules` 时，语音只播报一次，字幕不重复。
3. 修改、跳过、取消某个 occurrence 后，查询结果、例外记录、提醒 task 三者一致；重启后仍一致。
4. 每月 31 日、月末、2 月 29 日、跨年和午夜边界均有固定主机回归；当前仅 L1（远期日期窗口）完成真实百炼实板复测，L2/L5 仍是下一轮实板项，不能提前标记通过。
5. 若 L1 复现“远期日期漏查”，实现按查询日期窗口规划 occurrence，并增加服务层单测和 MCP 实板回归；禁止添加“超过三次就特殊查某年”的分支。

边界实板复测：使用同一固件和百炼 `qwen-audio-3.0-tts-flash + longanlingxi`，两轮“创建每月 31 号 -> 查询 2099-02-28”均完成。板端准确识别两句，查询结果明确播报该日没有一次性或周期日程；两轮均覆盖 phase 3/4/5/6、显示滚动和真实 MCP，最终 `in_drop/out_reject/short_write/in_i2s_err/out_i2s_err=0`。首次四轮扩展还发现，模型对月 31 号的解释可能拆成多句并持续约 69 秒，夹具默认 60 秒响应门限会提前报超时；将门限调到 120 秒后两轮通过。这是测试门限与模型回答长度的记录，不是设备丢帧或状态机失败，后续压力测试应把“长 TTS 回复时长”作为独立指标。

发现的问题属于“复合意图写入安全”，不是日期算法：

- 输入“每个月最后一天记账，查一下下个月最后一天有什么安排”时，设备先查询 9 月 30 日，随后又调用 `schedule.create` 创建“每月最后一天记账”；用户没有明确说“创建”或确认写入。
- 输入“每年九月一日体检，今年这天要做什么”时，同样先查询再创建每年 9 月 1 日规则。
- 输入“每年二月二十九日提醒我续证，明年有没有”时，系统在说明 2027 年不是闰年后仍创建了从 2028 年开始的周期提醒。

这三条都体现同一个根因：一个自然句中同时出现“事件描述/规则描述”和“查询疑问”，服务端模型把事件描述当成创建意图，设备端没有跨工具调用的确认闸门。不能通过屏蔽“每年”或某个日期来修；通用验收应改为：

1. 同一回合检测到读操作 + 写操作时，先只执行查询，播报候选和拟写入内容，进入待确认状态；
2. 只有用户明确说“创建/提醒我/确认/就这样”才调用 `schedule.create` 或 `schedule_rule.create`；“有没有/查一下/哪天/安排是什么”不能触发写入；
3. 用户拒绝、改日期或超时后，待确认写入必须失效，不能由旧的工具响应继续创建；
4. 每次写工具调用必须在日志中关联本回合 `generation`、确认文本和单一 mutation id，确保一次用户意图最多一次写入。

当前应归类为：

- 语音/意图模块问题：复合意图未确认、查询后隐式创建、屏幕虽正确滚动但播报顺序会让用户误以为已执行查询。
- 日程模块问题：长周期规则本身对 9 月 30 日和 2 月 29 日的计算结果符合当前规则实现；仍需补充按指定日期窗口直接规划的主机回归，验证远期 occurrence 不因固定 3 条上限漏查。

## 12. 行业能力边界对照表

这张表把“业界常见能力”“本项目当前能力”和“本轮测试动作”分开，避免把竞品存在的能力误当成我们已经支持：

| 能力 | Google Calendar / RFC / Graph 的常见语义 | VoiceLife 当前模型 | 测试结论 |
| --- | --- | --- | --- |
| 每日/每周/固定月日/固定年日 | RRULE `FREQ`，Graph daily/weekly/absoluteMonthly/absoluteYearly | daily/weekly/monthly/yearly | 已有；补自然语言和跨年测试 |
| 月末 | 通常用 BYSETPOS 或产品化的 last-day 语义 | monthly `last_day` | 已有；验证所有月长 |
| 每月第 N 个星期几 / 每年第 N 个星期几 | RFC `BYDAY + BYSETPOS`；Graph relativeMonthly/relativeYearly + index | 不支持 | 必须澄清，不得映射成月末 |
| 月 31 日遇短月 | 规则引擎按产品语义处理，不能无声改变日期 | 当前 planner 跳过短月 | 固定主机+实板验证，并播报下一次 |
| 2 月 29 日 | 允许规则存在，非闰年没有 occurrence | 当前 planner 跳过非闰年 | 实板已观察到 2027 跳过、2028 首次 |
| COUNT / UNTIL / 结束日期 | RRULE/Graph recurrence range 原生支持 | schema 有字段，但服务校验暂不支持 `occurrence_count` | 作为明确能力缺口，不得播报创建成功 |
| EXDATE/RDATE、单次修改/跳过 | Google/RFC 原生；Graph 有 occurrence/exception | exception modify/skip | 已有接口，需验证重启和提醒 task 一致 |
| 时区/DST | Google 使用 IANA 时区；Graph 使用事件时区 | 固定东八区、无 DST | 明确产品边界；跨 UTC 日必须测，不宣称通用时区 |
| 查询任意远期日期 | 产品 API 通常按 timeMin/timeMax 实例化查询 | 当前规则查询固定生成未来 3 条再过滤 | 高风险；需要按查询窗口规划的回归和修复 |
| 查询历史日期 | 产品 API 的时间窗口通常允许过去日期；是否返回历史 occurrence 由状态/例外决定 | 显式窗口现在可按历史 civil date 规划；无窗口仍只预览未来 3 条 | 主机回归覆盖；语音需验证“上周/去年”不会被误报为空 |
| 复合读写自然语言 | 产品 API 不替自然语言决定写入确认 | Linx 可能在一回合发多个 tools/call | 必须由设备/会话层加通用确认闸门 |

因此，后续测试不再把“支持周期”当成一个二元项，而是按“规则表达能力、实例展开窗口、异常/例外、时区、自然语言写入确认”五个正交维度覆盖。每个行业能力缺口都必须在语音中得到明确的“不支持/需要补充信息”，而不是静默降级。
