# 语音日程提醒工具：产品原型设计文档

这份原型文档根据最近提交的三个 Proposal 重新修正：P1 负责语音创建与查询，P2 只处理提醒触发后的关闭和稍后，P3 负责已有日程变更与周期控制。结论是：本期原型仍不做日历 GUI，先用语音对话和 IM 回执把 MVP 主流程说清楚。

请评审重点确认三件事：P1/P2/P3 的边界是否一致，语音与 IM 的分工是否清楚，以及高风险操作能不能避免误删、误改和误停周期事项。

> 状态：原型设计草案
> 日期：2026-07-21
> 关联 Issue：[#54](https://github.com/1024XEngineer/XE6-15/issues/54)
> 参考材料：战略决策文档 PR #51、用户故事文档 PR #52、MVP Proposal Issue #53、P1 PR #58、P2 PR #56、P3 PR #57

## 1. 原型结论

本期原型不是日历 App，也不是个人秘书。它只验证一条语音日程提醒主线：

```text
P1：用户说出安排，系统创建并能查回来
        |
        +-> P2：提醒到点触发，用户关闭或稍后
        |
        +-> P3：用户修改、跳过、暂停、终止或删除已有日程

公共规则：语音短反馈 + IM 回执 + 高风险确认 + 可撤销记录
```

这里有一个调整：上一版原型把“忽略本次”“标记已处理”放进 P2。按最新 P2 Proposal，这两个词容易和“事项完成/跳过”混在一起，本版收敛为两个提醒动作：关闭、稍后。只要用户想改日程本身，就转入 P3。

## 2. 最近三个 Proposal 对原型的修正

| 来源 | 已采纳到原型的修正 | 暂不采纳或待评审 |
| --- | --- | --- |
| P1：语音创建与查询（PR #58） | 创建前先补齐标题、时间、必要时长；冲突检查发生在真正创建前；查询长列表时语音只报摘要，完整列表走 IM | “帮我记住”即时记录会扩到个人记忆，本版不放进主流程；若团队要保留，需单独处理隐私和脱敏 |
| P2：提醒触发与即时响应（PR #56） | P2 只支持关闭和稍后；IM 受控回复与语音同效；多条提醒同时到达时要有活动提醒和歧义确认 | “已处理”“忽略本次”不再作为 P2 主命令 |
| P3：已有日程变更与周期控制（PR #57） | 修改、跳过、暂停、终止、删除都进入 P3；周期范围要说清本次、本次及以后、整个系列；单次事项的“跳过”要解释为取消并确认 | 暂停周期是否进入 MVP 还需团队拍板，本版保留为可评审流程，不作为必须实现项 |

## 3. 本期范围

### 3.1 本期做什么

| 能力 | 原型要表达什么 |
| --- | --- |
| 创建单次日程 | 用户一句话说出标题、开始时间、可选地点/备注；若需要冲突判断，必须有结束时间或时长 |
| 创建周期提醒 | 支持每天、每周、每月这类简单周期，不做复杂周期规则 |
| 查询日程 | 支持查今天、某一天、某一周、某一月、今年和下一条事项 |
| 创建前冲突提示 | 发现时间重叠时，先问用户是否仍然创建；用户拒绝时不留下日程 |
| 提醒触发 | 语音默认播标题和发生时间，地点、备注等详情发 IM |
| 提醒即时响应 | 用户能说“知道了”“不用再响了”“十分钟后提醒” |
| IM 受控回复 | 用户可在提醒回执里点“知道了”或“X 分钟后提醒”，只作用于这条提醒 |
| 修改已有日程 | 支持修改单次日程、周期实例、本次及以后或整个系列 |
| 跳过一次 | 周期事项可跳过本次；单次事项的跳过等同取消，必须确认 |
| 暂停或终止周期 | 暂停一段时间或终止后续提醒，执行前必须确认 |
| 删除日程 | 明确命中也要给删除结果和撤销；目标或范围不明时先确认 |
| 撤销恢复 | 修改、跳过、暂停、终止、删除后提供短时间撤销入口 |

### 3.2 本期明确不做

| 不做 | 原因 |
| --- | --- |
| 不做面向用户的日历 GUI | 当前目标是验证语音入口和 IM 回执，不把评审带向页面设计 |
| 不讨论语音入口载体 | 手机、音箱、耳机、车载都先不定，避免产品焦点跑偏 |
| 不做全天候监听 | 用户必须主动发起指令，不能静默捕获生活内容 |
| 不把即时记录做成个人记忆库 | 停车位置、密码、取件码、跨天模糊记忆先不进主流程 |
| 不在普通 IM 通知里明文展示敏感内容 | 如果后续保留取件码、密码类记录，必须只发认证私聊并默认脱敏 |
| 不做家庭或团队共享 | 多人权限、所有权和隐私播报会明显扩大范围 |
| 不做医疗照护承诺 | 可以提醒吃药，但不能承诺医疗效果或照护判断 |
| 不提前写技术实现细节 | 这份文档只定义产品原型和交互，后续技术设计另开 |

## 4. 交互原则

### 4.1 语音人设

语音反馈要像一个温柔、知性、办事稳当的东北大姐：不端着，也不油。可以说“妥了”“别急，我给你发回执了”，但不大面积使用方言，避免影响理解。

适合的语气：

- 温和，但有结论。
- 简短，但不糊弄。
- 高风险动作要认真确认，不能替用户猜。

不适合的语气：

- 过度卖萌。
- 过度客服腔。
- 大段解释系统能力。
- 在删除、永久停止周期事项时开玩笑。

### 4.2 语音和 IM 的分工

| 通道 | 职责 | 原型表现 |
| --- | --- | --- |
| 语音 | 快速操作、短反馈、必要追问 | “妥了，明天上午十点提醒你客户拜访。” |
| IM | 完整记录、候选项、复杂列表、确认和撤销入口 | 发送日程卡片、修改记录、删除回执和候选列表 |

语音不要一次性读长列表。超过 3 条时，语音只读数量、最近一条和列表位置，完整内容发到 IM。

IM 不是开放式日历入口。P2 的 IM 回复只允许处理当前提醒：知道了、X 分钟后提醒。查询、修改和删除仍以语音发起，或通过当前回执里的受控按钮选择。

### 4.3 提醒播报

P2 最新 Proposal 已经把规则收敛得更简单：语音默认只播标题和发生时间，详情走 IM。用户说“详细说说”时，再继续播地点和备注。

| 类型 | 语音播报 | IM 回执 |
| --- | --- | --- |
| 普通提醒 | “提醒：今天 15:00 和 Alex 开会。” | 展示标题、时间、地点、备注和操作 |
| 长标题提醒 | “提醒：今天 15:00 有一条客户拜访相关事项，详情我发你。” | 展示完整标题和备注 |
| 多条提醒 | 依次播报每条标题和时间；若用户事后只说“知道了”，先问指哪条 | 每条提醒单独一条回执 |
| 周期变更类提醒 | “这是每周重复事项。你要处理提醒，还是改这次安排？” | 展示影响范围和确认选项 |

### 4.4 风险分级确认

| 风险 | 示例 | 处理方式 |
| --- | --- | --- |
| 低风险 | 创建无冲突的单次日程、查询今天事项、当前提醒关闭或稍后 | 直接执行，短语音反馈，IM 留回执 |
| 中风险 | 修改唯一命中的单次日程、跳过一次周期事项 | 说明影响对象，执行后回读，保留撤销 |
| 高风险 | 删除、终止周期、修改整个系列、候选项不唯一、单次事项被“跳过” | 执行前确认，不允许静默处理 |

## 5. P1 原型：语音创建与查询

### 流程 1：一句话创建单次日程

目标：用户临时想到一件事时，不用打开日历 App。

```text
用户：明天上午十点客户拜访，A 座 1503，预计一小时。

系统语音：妥了，明天上午十点提醒你客户拜访。

IM 回执：
已创建日程
标题：客户拜访
时间：明天 10:00 - 11:00
地点：A 座 1503
操作：撤销 / 修改时间 / 查看明天日程
```

语音只回读标题和时间。地点、备注、预计时长放进 IM，避免语音反馈太长。

### 流程 2：缺少必要信息时只追问缺的部分

```text
用户：明天提醒我给王姐回电话。

系统语音：行，明天几点提醒你？

用户：下午两点。

系统语音：妥了，明天下午两点提醒你给王姐回电话。
```

如果用户创建的是会占用一段时间的日程，但没有说结束时间或时长，系统要按场景追问。

```text
用户：明天下午两点安排产品评审。

系统语音：这个评审预计多久？我好帮你看有没有时间冲突。

用户：一个小时。

系统语音：好，我先帮你看一下时间。
```

### 流程 3：创建前发现时间冲突

目标：冲突提示发生在真正创建前。用户拒绝时，不留下脏记录。

```text
用户：明天下午两点安排产品评审，预计一小时。

系统语音：明天下午两点到三点已有客户电话。仍然创建吗？

用户：先不建。

系统语音：行，那我没创建这条产品评审。
```

用户坚持保留冲突时：

```text
用户：没关系，还是创建。

系统语音：妥了，明天下午两点产品评审已创建，和客户电话时间重叠。

IM 回执：
已创建日程
标题：产品评审
时间：明天 14:00 - 15:00
冲突：明天 14:00 - 15:00 客户电话
操作：撤销 / 修改时间
```

系统不自动推荐新时间，也不自动移动另一条日程。

### 流程 4：创建周期提醒

```text
用户：每周五下午五点提醒我提交周报。

系统语音：妥了，每周五下午五点提醒你提交周报。下次是本周五。

IM 回执：
已创建周期提醒
标题：提交周报
周期：每周五 17:00
下次提醒：本周五 17:00
操作：跳过本次 / 修改本次 / 修改整个系列
```

本期只支持每天、每周、每月。用户说“每月最后一个周五”“隔周周三”这类复杂周期时，系统请用户改成更简单的表达。

### 流程 5：查询日程

目标：用户能问回今天、某个日期范围和下一条事项。语音只报摘要，完整列表进 IM。

| 用户说法 | 语音反馈 | IM 展示 |
| --- | --- | --- |
| 今天有什么事 | “今天有 4 件事，最近一件是下午三点和 Alex 开会。我把列表发你。” | 今天完整列表 |
| 明天上午有什么安排 | “明天上午有 2 件事：十点客户拜访，十一点半团队同步。” | 明天上午列表 |
| 下周有哪些提醒 | “下周有 9 条提醒，我按日期发你。” | 周视图文本列表 |
| 八月有哪些安排 | “八月有 12 条安排，我发你列表。” | 月度列表 |
| 今年有哪些长期提醒 | “今年仍在重复的提醒有 5 个，我发你列表。” | 周期提醒列表 |
| 下一条是什么 | “下一条是今天下午三点和 Alex 开会。” | 下一条日程卡片 |

本期不做开放式模糊搜索。用户问“这个月要交什么”时，系统只能在已记录标题里做明确匹配；匹配不准时请用户缩小范围。

### 待评审：即时记录是否进入本期

P1 Proposal 提到“帮我记住快递取件码”“车停哪了”这类即时记录。它有用，但会把产品从日程提醒推向个人记忆工具。

本版原型先不把它放进 MVP 主流程。若团队决定保留，只建议作为 P1 的受限补充：

- 只允许用户主动说“记一下”。
- 默认不保存密码、证件号等高敏内容。
- 含取件码、门禁码时，锁屏通知只显示“有一条私密记录”，正文只进已认证私聊。
- IM 回执默认脱敏，例如“取件码 ****1103”。

## 6. P2 原型：提醒触发与即时响应

### 流程 6：提醒触发后关闭

目标：用户只处理当前提醒，不改变底层日程。

```text
系统语音：提醒：今天 8:00 吃药。

用户：知道了。

系统语音：好，这条提醒关了。

IM 回执：
提醒已关闭
事项：吃药
时间：今天 8:00
说明：只关闭本次提醒，不修改日程
操作：10 分钟后再提醒 / 查看详情
```

这里不写“已处理”。系统不能替用户判断事情已经完成，只能知道这条提醒不再响。

### 流程 7：稍后提醒

```text
系统语音：提醒：15 分钟后开始周会。

用户：十分钟后再提醒我。

系统语音：好，10 分钟后再提醒你。本次日程时间没改。

IM 回执：
提醒已推迟
事项：周会
新提醒：10 分钟后
说明：只调整本次提醒，不修改日程时间
操作：知道了 / 再推迟 10 分钟
```

用户没说时长时要追问。

```text
用户：晚点提醒我。

系统语音：晚多久？你可以说十分钟、半小时或者一小时。
```

同一条提醒最多连续推迟 3 次。第 3 次到点后，系统提示“这是已经推迟过几次的提醒”，之后不再主动重复播报，只保留 IM 记录。

### 流程 8：IM 受控回复

目标：用户不方便说话时，也能处理这条提醒。

```text
IM 回执：
提醒：客户拜访
时间：今天 14:30
可回复：
- 知道了
- 10 分钟后提醒
- 30 分钟后提醒

用户在 IM 点击：10 分钟后提醒

IM 更新：
已推迟至 14:40
```

IM 回复只绑定当前这条提醒，不支持“今天有什么安排”“删掉这个”这种开放操作。

### 流程 9：多条提醒同时到达

目标：同时触发多条提醒时，系统不能把用户一句“知道了”随便绑定到某一条。

```text
系统语音：提醒：8:00 吃药。
系统语音：提醒：9:00 出门开会。

用户：知道了。

系统语音：你指的是吃药，还是出门开会？

用户：吃药。

系统语音：好，吃药这条提醒关了，出门开会那条还留着。
```

如果用户在某一条刚播完、下一条还没开始时说“知道了”，默认作用于刚播完的那条。所有提醒播完后再说，就要先确认目标。

## 7. P3 原型：已有日程变更与周期控制

### 流程 10：只修改本次周期事项

目标：用户临时改安排时，不用删除重建，也不误改周期规则。

```text
用户：把今天的日报推迟到晚上七点。

系统语音：妥了，只把今天的日报改到晚上七点。明天还是下午五点半。

IM 回执：
已修改本次周期事项
事项：日报
原时间：今天 17:30
新时间：今天 19:00
影响范围：仅本次
下一次：明天 17:30
操作：撤销修改
```

用户已经明确说“今天”，系统不再追问范围。

### 流程 11：周期范围不明确时先问清

```text
用户：把每周五的周报改到星期六上午。

系统语音：这是每周重复事项。你是只改本周，还是以后都改？

用户：以后都改。

系统语音：行，从本周开始改到每周六上午。上午几点？
```

这里不替用户默认“本次”或“整个系列”。范围不清时，多问一句比改错一串强。

### 流程 12：跳过一次周期事项

```text
用户：这周的周报跳过一次。

系统语音：妥了，只跳过这周五这一次，下周五还会提醒。

IM 回执：
已跳过本次
事项：提交周报
跳过：本周五 17:00
下次提醒：下周五 17:00
操作：撤销跳过
```

用户重复说同一句时：

```text
用户：这周周报跳过一次。

系统语音：这周这次已经跳过了，我没再重复操作。
```

### 流程 13：单次事项的“跳过”要解释为取消

```text
用户：跳过明天下午三点和 Alex 的会。

系统语音：这是单次日程，跳过就等于取消这场会。确定取消吗？

用户：确定。

系统语音：已取消明天下午三点和 Alex 的会，可以撤销。
```

用户没确认前，日程保持不变。

### 流程 14：暂停或终止周期事项

暂停是临时停一段时间，到期恢复。

```text
用户：出差这三天先暂停背单词提醒。

系统语音：我会暂停今天到周五的背单词提醒，周六恢复。确定吗？

用户：确定。

系统语音：妥了，周六恢复背单词提醒。
```

终止是停止之后所有提醒。

```text
用户：以后不用再提醒我提交周报了。

系统语音：这会停止之后所有周报提醒，确定终止吗？

用户：确定。

系统语音：已终止周报周期提醒，撤销窗口内还能恢复。
```

暂停是否进入 MVP 还需评审决定；终止属于高风险动作，必须确认。

### 流程 15：删除明确日程

```text
用户：删掉今天下午三点和 Alex 的会。

系统语音：已删除今天下午三点和 Alex 的会。删错了就说撤销。

IM 回执：
已删除日程
事项：和 Alex 开会
时间：今天 15:00
影响范围：单次日程
可撤销：短时间内
操作：撤销删除
```

### 流程 16：删除模糊或周期日程

```text
用户：删掉明天的项目会。

系统语音：我找到两个相关日程，先别删错。我发你选一下。

IM 候选：
1. 明天 10:00 项目周会
2. 明天 15:00 项目复盘会
回复：删 1 / 删 2 / 都不删
```

周期事项必须确认范围。

```text
用户：删掉健身课。

系统语音：健身课是重复日程。你要只删本周这一次，还是停止后续所有健身课？

IM 确认：
健身课，每周三 20:00
选择：
- 只删除本周三这一条
- 删除本周三之后的所有健身课
- 删除整个系列
- 取消操作
```

### 流程 17：修改后发生时间冲突

```text
用户：把今天和 Alex 的会改到下午四点。

系统语音：下午四点已有项目评审。仍然把 Alex 的会改到四点吗？

用户：还是改。

系统语音：改好了，两条日程会重叠，我在回执里标出来。
```

系统不自动移动项目评审，也不替用户取消其中一条。

### 流程 18：撤销刚才操作

```text
用户：撤销刚才的修改。

系统语音：恢复好了，Alex 的会已经回到原时间。

IM 回执：
已撤销修改
事项：和 Alex 开会
恢复为：今天 15:00
```

撤销回执按操作类型说明恢复了什么：修改恢复原安排，跳过恢复本次实例，暂停恢复原周期，终止恢复终止前状态，删除恢复被删除事项。

## 8. 异常和空状态

| 状态 | 语音处理 | IM 处理 |
| --- | --- | --- |
| 没听清 | “我没听清时间，你再说一遍几点？” | 展示已识别部分 |
| 缺少时长 | “这个安排预计多久？我好判断时间冲突。” | 保留待补信息 |
| 没找到日程 | “没找到明天下午的项目会。我发你明天的日程，你看看是哪条。” | 展示候选范围 |
| 候选过多 | “相关的有点多，我发你列表选。” | 展示最多 5 条，允许继续筛选 |
| 查询为空 | “今天没有已记录日程。” | 显示空列表和创建入口 |
| 多条提醒同时到达 | 依次播报；用户笼统回复时先问指哪条 | 每条提醒单独留回执 |
| IM 发送失败 | 语音正常播报，IM 后续重试 | 恢复后补发或标记失败 |
| 用户未回应提醒 | 不反复播报，避免打扰 | 保留未响应记录 |
| 操作失败 | “这次没改成，原日程没变。” | 显示失败原因和重试入口 |
| 撤销过期 | “已经过了可撤销时间，我不能直接恢复。” | 提供重新创建入口 |

## 9. 原型验收标准

这份原型通过评审，至少要满足下面几条。

1. 评审者能只看本文档，说清产品不是日历 GUI，也不是个人秘书，而是语音日程提醒工具。
2. 原型能按 P1/P2/P3 解释清楚：创建查询、提醒响应、已有日程变更分别归谁负责。
3. 创建日程时，缺时间要追问；需要判断冲突时，缺时长或结束时间也要追问。
4. 发现时间冲突时，系统在创建或修改前提示用户；用户拒绝时不留下新日程或变更。
5. 查询范围明确覆盖今天、某一天、某一周、某一月、今年和下一条事项；长列表只在 IM 展开。
6. P2 只支持关闭和稍后，不把“已处理”“忽略本次”当作主命令。
7. 提醒语音默认只播标题和发生时间；地点、备注和完整内容进入 IM。
8. IM 受控回复只作用于当前提醒，不成为开放式日历管理入口。
9. 多条提醒同时到达时，用户笼统回复必须触发目标确认。
10. P2/P3 边界不混淆：当前提醒稍后只改提醒状态，改时间、跳过本次、停止后续进入 P3。
11. 周期事项变更必须能说明影响范围：本次、本次及以后或整个系列。
12. 单次事项的“跳过”要解释为取消，并在执行前确认。
13. 对同一周期实例重复跳过时，系统提示已跳过，不重复变更。
14. 删除、终止、范围不明的周期操作必须先确认。
15. 修改、跳过、暂停、终止、删除都有与操作类型匹配的 IM 回执和撤销说明。
16. 涉及密码、取件码等敏感即时记录时，本期主流程不展示；若后续保留，必须脱敏并限制在认证私聊。
17. 文档不展开技术实现细节，后续设计另开。
