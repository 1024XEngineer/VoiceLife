# 语音日程提醒工具：产品原型设计文档

这份原型文档把 MS1 的战略决策和用户故事落成一套可评审的语音交互稿。结论是：本期原型不做日历 GUI，而是验证“语音操作 + IM 回执”能不能把日程创建、查询、提醒处理、修改、删除和跳过做清楚。

请评审重点确认三件事：这些场景是否足够支撑 MVP，语音和 IM 的分工是否清楚，以及高风险操作的确认方式是否能降低误删、误改周期日程的风险。

> 状态：原型设计草案
> 日期：2026-07-21
> 关联 Issue：[#54](https://github.com/1024XEngineer/XE6-15/issues/54)
> 参考材料：战略决策文档 PR #51、用户故事文档 PR #52、MVP Proposal Issue #53

## 1. 原型结论

本期原型不是“做一个日历 App”，也不是“做一个什么都能聊的个人秘书”。它只验证一条主线：

```text
用户说出安排
-> 系统听懂并补齐缺失信息
-> 到时提醒
-> 用户用语音处理提醒或修改已有日程
-> IM 留下可回看的结果
```

语音负责快，IM 负责稳。用户不方便看屏幕时，语音给短反馈；用户事后要确认细节时，IM 里有完整回执。

## 2. 本期范围

### 2.1 本期做什么

| 能力 | 原型要表达什么 |
| --- | --- |
| 创建单次日程 | 用户一句话说出时间、标题、地点或备注，系统记录并回执 |
| 创建周期提醒 | 支持每天、每周、每月这类简单周期，不做完整复杂规则 |
| 查询日程 | 支持查今天、某一天、某一周、某一月、今年和下一条事项 |
| 提醒触发 | 简单提醒一句话播完，复杂提醒先播摘要，详情发 IM |
| 即时处理提醒 | 用户能说“收到了”“十分钟后提醒”“先忽略”“标记已处理” |
| 修改已有日程 | 支持改单次日程和周期事项的本次实例 |
| 跳过一次 | 周期事项可跳过本次，不影响下一次提醒 |
| 删除日程 | 明确命中可删除，歧义或周期范围不明时先确认 |
| 撤销恢复 | 删除或修改后提供短时间撤销入口 |
| IM 回执 | 所有关键动作留下文本记录，包含结果、影响范围和撤销提示 |

### 2.2 本期明确不做

| 不做 | 原因 |
| --- | --- |
| 不做面向用户的日历 GUI | 战略已经收敛为语音主入口，本期先验证语音和回执 |
| 不讨论语音入口载体 | 手机、音箱、耳机、车载都先不定，避免产品焦点跑偏 |
| 不做全天候监听 | 用户必须主动发起指令，不能静默捕获生活内容 |
| 不做个人记忆库 | 停车位置、密码、单号、跨天模糊记忆先不进 MVP |
| 不做家庭或团队共享 | 多人权限、所有权和隐私播报会明显扩大范围 |
| 不做医疗照护承诺 | 可以提醒吃药，但不能承诺医疗依从性或照护判断 |
| 不提前写架构、字段、接口 | 这份文档只定义产品原型和交互，不做技术设计 |

## 3. 交互原则

### 3.1 语音人设

语音反馈要像一个温柔、知性、办事稳当的东北大姐：不端着，也不油。可以说“妥了”“别急，我给你发回执了”，但不大面积使用方言，避免影响理解。

适合的语气：

- 温和，但有结论。
- 简短，但不糊弄。
- 高风险动作要认真确认，不能为了显得聪明就替用户猜。

不适合的语气：

- 过度卖萌。
- 过度客服腔。
- 大段解释系统能力。
- 在删除、永久停止周期事项时开玩笑。

### 3.2 语音和 IM 的分工

| 通道 | 职责 | 原型表现 |
| --- | --- | --- |
| 语音 | 快速操作、短反馈、必要追问 | “妥了，明天上午十点提醒你客户拜访。” |
| IM | 完整记录、候选项、复杂列表、撤销入口 | 发送日程卡片、修改记录、删除回执和候选列表 |

语音不要一次性读长列表。超过 3 条时，语音只读摘要，把完整内容发到 IM。

### 3.3 简单提醒和复杂提醒

简单提醒指一句话就能说清的提醒，例如“晚上 9 点背单词”。复杂提醒指包含地点、备注、周期范围、冲突或多项内容的提醒。

| 类型 | 语音播报 | IM 回执 |
| --- | --- | --- |
| 简单提醒 | “到点了，晚上 9 点背单词。” | 记录标题、时间、处理按钮 |
| 复杂提醒 | “15 分钟后客户拜访，在 A 座 1503。我把地址和备注发你了。” | 展示标题、时间、地点、备注、相关冲突 |
| 多条提醒 | “今天上午有 3 件事，我先发你列表。要听第一件吗？” | 展示完整列表，允许选择、稍后、忽略 |
| 高风险提醒 | “这是每周重复事项。你是只跳过今天，还是以后都停？” | 展示影响范围和确认选项 |

### 3.4 风险分级确认

| 风险 | 示例 | 处理方式 |
| --- | --- | --- |
| 低风险 | 创建明确单次日程、查询今天事项、当前提醒稍后 10 分钟 | 直接执行，短语音反馈，IM 留回执 |
| 中风险 | 修改单次日程、跳过本次周期事项 | 说明影响对象，必要时确认 |
| 高风险 | 删除、停止后续周期提醒、修改整个系列、候选项不唯一 | 必须先确认，不允许静默执行 |

## 4. 核心流程原型

### 流程 1：一句话创建单次日程

目标：用户临时想到一件事时，不用打开日历 App。

```text
用户：明天上午十点客户拜访，A 座 1503。

系统语音：妥了，明天上午十点提醒你客户拜访，地点是 A 座 1503。

IM 回执：
已创建日程
标题：客户拜访
时间：明天 10:00
地点：A 座 1503
操作：撤销 / 修改时间 / 查看明天日程
```

缺少信息时只追问缺的部分。

```text
用户：明天提醒我给王姐回电话。

系统语音：行，明天几点提醒你？

用户：下午两点。

系统语音：妥了，明天下午两点提醒你给王姐回电话。
```

### 流程 2：创建周期提醒

目标：用户不用重复创建固定事项。

```text
用户：每周五下午五点提醒我提交周报。

系统语音：妥了，每周五下午五点提醒你提交周报。下次是本周五。

IM 回执：
已创建周期提醒
标题：提交周报
周期：每周五 17:00
下次提醒：本周五 17:00
操作：跳过本次 / 修改本次 / 修改整个系列
```

原型边界：本期只支持常见周期。用户说“每个工作日、节假日除外、每季度最后一个周五”时，先提示不支持复杂规则，让用户改成更简单的表达。

### 流程 3：查询日程

目标：用户能用自然语言查回自己刚记的事和某个时间范围内的事项。

| 用户说法 | 语音反馈 | IM 展示 |
| --- | --- | --- |
| 今天有什么事 | “今天有 4 件事，最近一件是下午三点和 Alex 开会。我把列表发你。” | 今天完整列表 |
| 明天上午有什么安排 | “明天上午有 2 件事：十点客户拜访，十一点半团队同步。” | 明天上午列表 |
| 下周有哪些提醒 | “下周有 9 条提醒，我按日期发你。” | 周视图文本列表 |
| 这个月要交什么 | “这个月有 3 个带提交含义的事项，我发你确认。” | 关键词命中的事项列表 |
| 今年有哪些长期提醒 | “今年仍在重复的提醒有 5 个，我发你列表。” | 周期提醒列表 |
| 下一条是什么 | “下一条是今天下午三点和 Alex 开会。” | 下一条日程卡片 |

查询结果超过 3 条时，语音只读数量、最近一条和列表位置，不完整读完。

### 流程 4：提醒触发和即时处理

目标：提醒到来后，用户不打开界面也能处理当前提醒。

```text
系统语音：15 分钟后开始周会。

用户：十分钟后再提醒我。

系统语音：好，10 分钟后再提醒你。本次日程时间没改。

IM 回执：
提醒已延后
事项：周会
原提醒：15 分钟前
新提醒：10 分钟后
说明：只调整本次提醒，不修改日程时间
操作：撤销延后 / 标记已处理
```

边界要说清：

- “十分钟后再提醒我”只改提醒状态，属于当前提醒处理。
- “把周会改到晚上八点”修改日程时间，进入已有日程变更。
- “今天这次不参加了”影响周期实例，进入跳过或取消本次确认。

### 流程 5：修改已有日程

目标：用户临时改安排时，不用删除重建，也不误改周期规则。

```text
用户：把这周五的周报改到星期六上午十点。

系统语音：这是每周五的周期提醒。你是只改这周这一次，对吧？

用户：对，只改这次。

系统语音：改好了。这周改到星期六上午十点，下周还是星期五下午五点。

IM 回执：
已修改本次周期事项
标题：提交周报
本次时间：本周六 10:00
后续规则：仍为每周五 17:00
操作：撤销 / 改为之后都这样
```

### 流程 6：跳过一次周期事项

目标：用户只取消本次，不影响下一次。

```text
用户：这周的健身课跳过一次。

系统语音：妥了，只跳过这周三的健身课，下周三还会提醒。

IM 回执：
已跳过本次
事项：健身课
跳过：本周三 20:00
下次提醒：下周三 20:00
操作：撤销跳过 / 停止整个系列
```

### 流程 7：删除明确日程

目标：用户取消安排后能快速清理，并有撤销机会。

```text
用户：删掉今天下午三点和 Alex 的会。

系统语音：已删除今天下午三点和 Alex 的会。要是删错了，可以说撤销。

IM 回执：
已删除日程
标题：和 Alex 开会
时间：今天 15:00
可撤销：10 分钟内
操作：撤销删除
```

### 流程 8：删除模糊或周期日程

目标：语音说不准时，系统不能替用户赌。

```text
用户：删掉明天的项目会。

系统语音：我找到两个相关日程，先别删错。我发你选一下。

IM 候选：
1. 明天 10:00 项目周会
2. 明天 15:00 项目复盘会
回复：删 1 / 删 2 / 都不删
```

周期事项必须确认范围。

```text
用户：删掉健身课。

系统语音：健身课是重复日程。你要删本周这一次，还是整个系列？

IM 确认：
健身课，每周三 20:00
选择：
- 只删除本周三这一条
- 删除本周三之后的所有健身课
- 删除整个系列
- 取消操作
```

### 流程 9：撤销刚才操作

目标：用户发现误删、误改后能马上恢复。

```text
用户：撤销刚才删除。

系统语音：恢复好了，今天下午三点和 Alex 的会已经回来了。

IM 回执：
已撤销删除
恢复事项：和 Alex 开会
时间：今天 15:00
提醒：恢复为原设置
```

## 5. 异常和空状态

| 状态 | 语音处理 | IM 处理 |
| --- | --- | --- |
| 没听清 | “我没听清时间，你再说一遍几点？” | 展示已识别部分 |
| 没找到日程 | “没找到明天下午的项目会。我发你明天的日程，你看看是哪条。” | 展示候选范围 |
| 候选过多 | “相关的有点多，我发你列表选。” | 展示最多 5 条，允许继续筛选 |
| 查询为空 | “今天没有已记录日程。” | 显示空列表和创建入口 |
| 操作失败 | “这次没改成，原日程没变。” | 显示失败原因和重试入口 |
| 撤销过期 | “已经过了可撤销时间，我不能直接恢复。” | 提供重新创建入口 |

## 6. 原型验收标准

这份原型通过评审，至少要满足下面几条。

1. 评审者能只看本文档，说清产品不是日历 GUI，也不是个人秘书，而是语音日程提醒工具。
2. 创建、查询、提醒即时处理、修改、删除、跳过、撤销都有可读的语音和 IM 样例。
3. 简单提醒和复杂提醒的播报差异明确：简单一句话，复杂先摘要，详情进 IM。
4. 查询范围明确覆盖今天、某一天、某一周、某一月、今年和下一条事项。
5. P2/P3 边界在原型中不混淆：提醒稍后只改提醒状态，改时间、跳过本次、删除周期实例进入日程变更。
6. 删除、修改周期、停止后续这类高风险动作必须先确认影响范围。
7. 文档不写架构、字段、接口和实现方案，后续技术设计另开 Issue 或 PR。
