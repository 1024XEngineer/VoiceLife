# 语音日程管理工具：MS1 战略决策文档

本轮战略决策将 XE6-15 从“GitHub 个人项目管理工具”转向“基于语音交互的个人日程与提醒管理工具”。结论是：先做语音优先的软件型 MVP，服务有零散事项和周期提醒需求的个人用户；不做硬件音箱、不做全天候记忆、不做团队共享日历。

请组内先确认四件事：目标用户是否收窄到“愿意用语音管理个人日程的人”，MVP 是否只做“加、查、改、删、跳过、提醒即时处理”，是否接受“高风险动作先确认、所有动作留 IM 回执”的交互原则，以及是否把硬件、位置触发、被动捕获和跨人协作放到后续。

## 1. 为什么改方向

原战略文档已经把“GitHub 个人项目管理工具”讲清楚了：只读取与本人相关的 Issue、PR、Review，做个人任务池、优先级排序和重排。这个文档的方法是好的，尤其是目标用户、数据边界、要什么/不要什么、Proposal 地图和反证条件。

但题目已经变了，旧方向不能继续当产品目标。新方向不是 GitHub 任务排序，而是语音场景下的日程管理。旧文档只保留写法和决策粒度，不保留产品结论。

本轮要回答的是另一组问题：

- 用户为什么要用语音，而不是打开日历 App？
- 日程管理里哪些动作适合语音先做？
- 语音听错、说不清、周期事项范围不明时，系统如何避免误操作？
- 8 周内先证明哪条主流程，而不是把智能音箱、AI 记忆、家庭共享、硬件方案一起做进去？

## 2. 战略决策摘要

| 决策项 | 本期选择 |
| --- | --- |
| 做什么 | 做一个语音优先的个人日程与提醒助手，支持用户用自然语言创建、查询、修改、删除、跳过事项，并在提醒触发时快速处理 |
| 为谁做 | 愿意使用语音、日常有零散事项和周期提醒需求、经常处在不方便打字或看屏幕场景下的个人用户 |
| 核心问题 | 现有日历/提醒工具能记录事项，但用户临时想到、双手不空、刚被打断或只想快速改一条周期提醒时，打开 App 的成本太高；语音助手又容易因为听错或范围不清造成误操作 |
| 价值主张 | 用户一句话说出安排，系统只追问缺失信息；低风险动作快速完成，高风险动作先确认；所有关键操作留下可回看的 IM 回执，误删误改可以撤销 |
| 产品形态 | 软件优先：语音输入 + 语音反馈 + IM/文本回执。可以运行在手机或原型页面中，不要求本期自研硬件 |
| 数据边界 | 只保存用户明确创建或修改的日程/提醒、必要的结构化字段、操作回执和短期上下文；不做全天候录音，不做被动记忆库 |
| MVP 主线 | 语音创建日程 -> 系统确认/补槽 -> 到时提醒 -> 用户说“稍后/跳过/改时间/删除” -> 系统执行并留下回执 |
| 本期不做 | 不做硬件设备、不做共享家庭日历、不做医疗建议、不做位置触发、不做外部信号监控、不做跨天模糊记忆检索、不做自动监听和静默捕获 |

## 4. 本期目标用户

### 4.1 核心用户

本期只服务一类用户：

> 有零散事项和周期提醒需求，并且愿意在走路、开会间隙、做家务、通勤、照顾家人等不方便操作屏幕的场景下，用语音管理个人安排的人。

这个定义比“所有日程用户”窄，也比“AI 记忆助手用户”窄。

核心特征：

1. 日常会突然产生小安排：会议、缴费、取快递、联系某人、客户预约、周报、用药提醒。
2. 有周期性事项：每周会议、每晚背单词、每月缴费、固定复诊、定期提交材料。
3. 经常发生临时变化：改时间、取消本次、跳过一次、之后都改、误删后恢复。
4. 愿意对设备说话，并接受语音反馈或 IM 回执。
5. 需要的是“马上记住并按时提醒”，不是复杂项目排期。

### 4.2 暂不作为核心用户

| 用户/场景 | 为什么暂不作为本期核心 |
| --- | --- |
| 阿尔茨海默症患者或严肃医疗照护用户 | 需求真实，但医疗和照护风险高，不能用普通提醒能力包装成医疗产品 |
| 家庭共享设备用户 | 需要多用户身份、隐私播报、所有权和权限规则，超出 MS1/MVP |
| 商务团队共享日历用户 | 会引入邀请、改他人日程、会议室、权限和冲突仲裁，不是个人助手 |
| 硬件音箱/可穿戴用户 | 硬件路线会把项目重心转向设备、唤醒词、端云架构和供应链 |
| 全天候记忆用户 | 被动捕获、跨天模糊检索、长期记忆版本线都很大，本期不能混入日程 MVP |

## 5. 用户故事收敛

近期活动里出现了很多故事。战略上只把下面 7 条收进 MVP 方向，其余留作后续。

### 故事 1：一句话创建单次日程

- **作为** 正在路上或刚结束沟通的职场用户
- **我希望** 说“明天上午十点客户拜访，A 座 1503”就能创建日程
- **以便于** 我不用打开 App 逐项填写，也不用担心回头忘记地点

验收例子：

- **Given:** 当前没有同名同时间日程
- **When:** 用户说“明天上午十点客户拜访，A 座 1503”
- **Then:** 系统创建日程，语音反馈时间和标题，并在 IM 回执中保留地址

### 故事 2：创建周期提醒

- **作为** 有固定习惯或固定任务的个人用户
- **我希望** 说“每周五下午五点提醒我提交周报”就能建立周期提醒
- **以便于** 我不用每周重复创建同一件事

验收例子：

- **Given:** 用户没有同名周期提醒
- **When:** 用户说“每周五下午五点提醒我提交周报”
- **Then:** 系统创建每周五 17:00 的周期提醒，并反馈“下次提醒是本周五下午五点”

### 故事 3：查询刚记下或即将发生的日程

- **作为** 对刚才录入内容不放心的用户
- **我希望** 能问“明天上午那个客户地址再说一遍”
- **以便于** 我确认系统确实记住了关键细节

验收例子：

- **Given:** 用户刚创建“明天上午十点客户拜访，A 座 1503”
- **When:** 用户问“明天上午那个客户地址再说一遍”
- **Then:** 系统回答“A 座 1503”，并说明对应日程是“明天上午十点客户拜访”

### 故事 4：修改已有事项

- **作为** 经常临时改安排的用户
- **我希望** 说“把这周五的周报改到星期六上午十点”
- **以便于** 我不用删除后重建，也不会误改以后每周的规则

验收例子：

- **Given:** 用户有“每周五下午五点提交周报”的周期提醒
- **When:** 用户说“把这周五的周报改到星期六上午十点”
- **Then:** 系统只修改本周这一次，并反馈“下周仍然是星期五下午五点”

### 故事 5：跳过一次周期事项

- **作为** 有周期事项但临时不用执行的用户
- **我希望** 说“这周的周报跳过一次”
- **以便于** 我取消本次提醒，但不影响下一次周期

验收例子：

- **Given:** 用户有“每周五下午五点提交周报”的周期提醒
- **When:** 用户说“这周的周报跳过一次”
- **Then:** 系统标记本周这一条为跳过，并反馈“下次仍然是下周五下午五点”

### 故事 6：删除日程并可撤销

- **作为** 临时取消安排的用户
- **我希望** 能说“删掉今天下午三点和 Alex 的会”
- **以便于** 我快速清理已经取消的安排，并在删错时马上恢复

验收例子：

- **Given:** 用户有唯一一条“今天下午三点和 Alex 开会”
- **When:** 用户说“删掉今天下午三点和 Alex 的会”
- **Then:** 系统删除该日程，并反馈“已删除，可以说撤销恢复”

### 故事 7：提醒触发时即时处理

- **作为** 正在忙的用户
- **我希望** 提醒响起时直接说“十分钟后提醒”“今天跳过”“改到今晚八点”
- **以便于** 我不用打开 App，也能把当前提醒处理掉

验收例子：

- **Given:** 系统正在提醒“15 分钟后开始周会”
- **When:** 用户说“十分钟后提醒我”
- **Then:** 系统将提醒延后 10 分钟，并反馈新的提醒时间

## 6. 本期要什么

本期不追求“会聊很多”，只跑通一条可靠的语音日程主流程：

1. 用户可以用语音创建单次日程，至少支持标题、日期、时间、地点/备注。
2. 用户可以用语音创建周期提醒，至少支持每天、每周、每月三类常见规则。
3. 系统只追问缺失槽位，例如缺时间就问时间，不让用户从头重说。
4. 系统对低风险动作使用短反馈，例如“好，明天八点提醒你吃药”。
5. 系统对高风险动作使用显式确认，例如删除、覆盖、永久停止周期提醒。
6. 用户可以查询今天、明天、下一条、某个关键词相关的日程。
7. 用户可以修改单次日程，也可以修改周期事项中的某一次。
8. 涉及周期事项时，系统必须区分本次、之后全部、整个系列。
9. 用户可以跳过一次周期事项，并保留下一次提醒。
10. 用户可以删除日程，删除后提供短时间撤销。
11. 提醒触发时，用户可以说“稍后”“跳过”“取消”“改到某时间”。
12. 每次创建、修改、删除、跳过都留下 IM/文本回执，方便用户事后确认。

## 7. 本期明确不做

| 维度 | 本期不做 | 原因 |
| --- | --- | --- |
| 硬件 | 不做智能音箱、耳机、可穿戴或车载设备 | 8 周内验证产品价值，硬件会转移重心 |
| 全天候监听 | 不做静默捕获、被动录音、自动判断哪句话值得记 | 隐私和信任成本太高，且不是日程管理的最短路径 |
| 个人记忆库 | 不做停车位置、密码、单号、跨天模糊记忆检索 | 这些是“记忆助手”，不是本期日程 MVP |
| 位置触发 | 不做“到楼下买牙膏”“到银行提醒取钱” | 需要地理围栏、误触发抑制和场景判断，复杂度高 |
| 外部信号触发 | 不做“老张三点没回消息就提醒我” | 需要接入 IM/邮件等外部系统并持续监控 |
| 团队协作 | 不做共享日历、邀请他人、家庭成员所有权、会议室冲突 | 权限和协作规则会把个人产品变成团队产品 |
| 医疗产品 | 不做用药依从性、病情管理、照护判断 | 可以做普通提醒，不能承诺医疗效果 |
| 商业模式 | 不写订阅、硬件销售、SaaS API 作为本期决策 | MS1 先证明 MVP，不做商业路线展开 |
| 通用 AI 助理 | 不做天气、闲聊、知识问答、会议纪要、自动总结 | 会冲淡“语音日程管理”的验证重点 |

## 8. 关键取舍

| 决策 | 备选方向 | 本期选择与理由 |
| --- | --- | --- |
| 产品边界 | 日程管理 / 个人记忆助手 / 智能音箱 | 选日程管理。近期用户故事中“加、改、删、跳过、提醒”最集中，也最容易验证 |
| 产品形态 | 硬件设备 / 手机 App / IM 机器人 / Web 原型 | 选软件优先，原型可用 Web 或手机模拟；IM 回执作为辅助通道，不把 IM 做成主产品 |
| 交互原则 | 默认确认 / 默认不确认 / 按风险分层确认 | 选按风险分层。普通创建用短反馈，删除、永久停止、范围不明必须确认 |
| 周期事项 | 本期不做 / 只做简单周期 / 做完整 RRULE | 选简单周期 + 清楚范围。每天/每周/每月够用，先把“本次/以后/整个系列”讲清楚 |
| 删除和修改 | 用户说了就执行 / 所有都二次确认 / 明确命中执行、歧义确认 | 选明确命中执行、歧义确认。语音要快，但不能赌用户想法 |
| 回执 | 只语音播报 / 只文本记录 / 语音短反馈 + IM 回执 | 选语音短反馈 + IM 回执。语音听过即逝，回执能降低不放心和误操作成本 |
| 冲突处理 | 本期不做 / 冲突时拒绝 / 提示冲突后允许用户确认 | 选提示后确认。用户可能故意保留重叠安排，系统不应替他决定 |

## 9. MVP 核心假设

> 对于有零散事项和周期提醒需求的用户，只要语音交互能做到“说得快、问得少、错了能改、删改可撤销”，它就可能比打开日历 App 更适合临时录入和临时变更日程。

这个假设有三层：

1. **语音入口有价值**：用户在走路、做饭、开会间隙、通勤等场景下，愿意用一句话创建或处理提醒。
2. **风险控制决定信任**：用户真正害怕的不是多说一句，而是系统听错后静默误删、误改、误停周期提醒。
3. **回执降低记忆负担**：语音反馈听完就过去了，IM/文本回执能让用户事后确认“到底记了什么、改了什么”。

反证条件：

1. 用户认为打开日历 App 比语音更快、更安心。
2. 多数真实表达都需要两轮以上澄清，语音效率不成立。
3. 用户不信任系统处理删除、修改、周期范围，频繁回 App 检查。
4. 周期提醒、跳过一次、改本次这些场景频率不够高。
5. IM 回执无人查看，无法降低语音听过即逝的问题。

如果出现这些反证，应先缩小到“语音创建提醒”单点，不继续扩展高级故事。

## 10. Proposal 地图

```text
用户说出安排
      |
      v
Proposal 1：语音创建与查询
      |
      v
Proposal 2：提醒触发与即时处理
      |
      v
Proposal 3：已有事项变更与风险确认
      |
      v
语音反馈 + IM 回执 + 可撤销记录
```

三个 Proposal 有依赖关系，不建议并行发散。先证明用户愿意用语音创建和查询，再做提醒触发时的即时处理，最后把修改、删除、跳过和周期范围控制补完整。

| Proposal | 要解决的窄问题 | 本期范围 | 明确不做 | 验收方向 |
| --- | --- | --- | --- | --- |
| 1. 语音创建与查询 | 用户想到安排时不想打开 App 填表 | 单次日程、简单周期提醒、缺槽追问、今天/明天/下一条/关键词查询、IM 回执 | 位置触发、外部信号触发、被动记忆、共享日历 | 用户能用一句话完成多数新增事项，并能查回刚录入的关键细节 |
| 2. 提醒触发与即时处理 | 提醒响起时，用户不想进入 App 才能处理 | 到时提醒、稍后提醒、今天跳过、改到某时间、停止后续提醒的确认 | 多设备联动、复杂通知中心、紧急度模型 | 用户在提醒播报中能用一句话完成当前处理 |
| 3. 已有事项变更与风险确认 | 语音修改/删除容易误操作，尤其是周期事项 | 修改单次、修改本次周期实例、跳过一次、删除、撤销、冲突提示、范围确认 | 完整 RRULE、多人日历冲突、自动替用户改计划 | 用户能清楚知道影响的是本次、之后全部还是整个系列，且能撤销刚才操作 |

## 11. 基本概念与信息结构

这部分给后续架构设计做输入。

### 11.1 核心概念

| 概念 | 定义 |
| --- | --- |
| 事项 | 用户需要在某个时间、某段时间或某个周期内记住并处理的对象 |
| 单次事项 | 只发生一次的事项，例如“明天十点客户拜访” |
| 周期事项 | 按规则重复出现的事项，例如“每周五下午五点提交周报” |
| 周期实例 | 周期事项中的某一次，例如“本周五这一次周报” |
| 提醒 | 系统在某个时间触发的播报或通知，可以绑定事项 |
| 跳过 | 只让某一次周期实例不再提醒，不改变周期规则 |
| 暂停 | 在一个时间范围内不触发周期提醒，到期后恢复 |
| 终止 | 停止整个周期事项，属于高风险动作 |
| 回执 | 每次关键操作后的文本记录，包含原内容、新内容、影响范围和撤销入口 |
| 撤销窗口 | 删除或修改后允许用户恢复的短时间窗口 |

### 11.2 最小数据字段

| 对象 | 关键字段 |
| --- | --- |
| ScheduleItem | id、title、start_time、end_time、note、location、status、source_text、created_at、updated_at |
| RecurrenceRule | item_id、frequency、interval、weekday/monthday、start_date、end_date/status |
| OccurrenceOverride | item_id、occurrence_time、override_type、new_time、skipped、deleted |
| Reminder | item_id、trigger_time、channel、state、last_triggered_at |
| OperationReceipt | operation_type、before_snapshot、after_snapshot、scope、本次语音原文、created_at、undo_expires_at |
| ConversationContext | current_item_id、last_operation_id、expires_at |

## 12. 验收标准

战略文档通过的标准不是“内容看起来完整”，而是能指导 MS1/MS2 继续拆 Proposal 和原型。

1. 团队能用一句话复述新方向：语音优先的个人日程与提醒管理工具。
2. 团队能说清目标用户：有零散事项和周期提醒需求，并愿意用语音的人。
3. 团队能解释为什么不做硬件、不做被动记忆、不做共享日历。
4. 原型能演示至少 6 条主流程：创建、查询、修改、删除、跳过、提醒即时处理。
5. 原型中所有高风险动作都有确认或撤销：删除、永久停止周期、周期范围不明、冲突覆盖。
6. 每个关键动作都有 IM/文本回执，不只依赖语音播报。
7. 用户故事能映射到 Proposal，而不是散落成互不相干的功能清单。
8. 后续架构能直接依据“事项、周期规则、周期实例、回执、上下文”建模型。
