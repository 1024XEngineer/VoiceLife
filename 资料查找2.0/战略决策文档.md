# 语音日程提醒工具：MS1 战略决策文档

本轮战略决策将 XE6-15 从“GitHub 个人项目管理工具”转向“语音日程提醒工具”。结论是：最终定位就是语音日程提醒工具，不扩成个人秘书；MS1/MVP 只验证日程与提醒管理这一条主线。

本期产品只假设存在语音入口和 IM/文本回执通道，不设计 GUI，不依赖摄像头、位置、传感器等其他能力，也不讨论语音入口的具体载体。8 周内先把用户明确说出的日程事项做准、说清、可查、可撤销。

请组内先确认四件事：是否接受“语音日程提醒工具”的定位，MVP 是否按最近 Proposal 收敛为“语音创建/查询 -> 提醒响应 -> 已有日程变更”，是否接受“高风险动作先确认、所有动作留 IM 回执”的交互原则，以及是否把 GUI、入口载体、位置触发、被动捕获和跨人协作放到后续。

## 1. 为什么改方向

原战略文档已经把“GitHub 个人项目管理工具”讲清楚了：只读取与本人相关的 Issue、PR、Review，做个人任务池、优先级排序和重排。这个文档的方法是好的，尤其是目标用户、数据边界、要什么/不要什么、Proposal 地图和反证条件。

但题目已经变了，旧方向不能继续当产品目标。新方向不是 GitHub 任务排序，也不是个人秘书，而是专注日程和提醒处理的语音工具。旧文档只保留写法和决策粒度，不保留产品结论。

本轮要回答的是另一组问题：

- 最终定位和 MVP 边界如何表达？
- 用户为什么要用语音，而不是打开日历 App？
- 日程管理里哪些动作适合语音先做？
- 语音听错、说不清、周期事项范围不明时，系统如何避免误操作？
- 8 周内先证明哪条主流程，而不是把 GUI、AI 记忆、家庭共享和入口载体方案一起做进去？

## 2. 战略决策摘要

| 决策项 | 本期选择 |
| --- | --- |
| 做什么 | 做语音日程提醒工具；MS1/MVP 先跑通语音创建/查询、提醒响应、已有日程变更与周期控制 |
| 为谁做 | 愿意使用语音、日常有零散事项和周期提醒需求、经常处在不方便打字或看屏幕场景下的个人用户 |
| 核心问题 | 现有日历/提醒工具能记录事项，但用户临时想到、双手不空、刚被打断或只想快速改一条周期提醒时，打开 App 的成本太高；语音助手又容易因为听错或范围不清造成误操作 |
| 价值主张 | 用户一句话说出安排，系统只追问缺失信息；低风险动作快速完成，高风险动作先确认；所有关键操作留下可回看的 IM 回执，误删误改可以撤销 |
| 产品形态 | 产品以语音作为主要操作入口，支持语音反馈，并通过 IM 提供可回看的日程记录、操作回执和异常确认。本期不提供面向用户的日历 GUI |
| IM 角色 | 语音负责操作，IM 负责持久化确认和异常修复。IM 不做开放式日历管理入口，只允许确认、撤销、选择范围这类受控回复；语音没听清时以 IM 回执为准 |
| 数据边界 | 只保存用户明确创建或修改的日程/提醒、必要的结构化信息、操作回执和短期上下文；不做全天候录音，不做被动记忆库 |
| MVP 主线 | 语音创建或查询日程 -> 系统补齐必要信息并做冲突检查 -> 主提醒按用户指定时间触发，必要时给 15 分钟弱提醒 -> 用户关闭或稍后；若要改日程，进入 P3 |
| 本期不做 | 不做面向用户的日历 GUI、不讨论入口载体、不做共享家庭日历、不做医疗建议、不做位置/传感器触发、不做外部信号监控、不做长期个人记忆库、不做自动监听和静默捕获，不写数据库字段、接口或技术实现方案 |

## 4. 本期目标用户

### 4.1 核心用户

本期只服务一类用户：

> 有零散事项和周期提醒需求，并且愿意在走路、开会间隙、做家务、通勤、照顾家人等不方便操作屏幕的场景下，用语音管理个人安排的人。

这个定义比“所有日程用户”窄，也比“AI 记忆助手用户”窄。

核心特征：

1. 日常会突然产生小安排：会议、缴费、取快递、联系某人、客户预约、周报、用药提醒。
2. 有周期性事项：每周会议、每晚背单词、每月缴费、固定复诊、定期提交材料。
3. 经常发生临时变化：改时间、取消本次、跳过一次、之后都改、误删后恢复。
4. 愿意对设备说话，并接受语音反馈或 IM 回执。
5. 需要的是“马上记住、能查回来、到点提醒”，不是复杂项目排期。

### 4.2 暂不作为核心用户

| 用户/场景 | 为什么暂不作为本期核心 |
| --- | --- |
| 阿尔茨海默症患者或严肃医疗照护用户 | 需求真实，但医疗和照护风险高，不能用普通提醒能力包装成医疗产品 |
| 家庭共享设备用户 | 需要多用户身份、隐私播报、所有权和权限规则，超出 MS1/MVP |
| 商务团队共享日历用户 | 会引入邀请、改他人日程、会议室、权限和冲突仲裁，不是个人助手 |
| 专用设备用户 | 设备路线会把项目重心转向唤醒词、端云方案和供应链 |
| 全天候记忆用户 | 被动捕获、跨天模糊检索、长期记忆版本线都很大，本期不能混入日程 MVP；用户主动说出的小事只按短期记录处理 |

## 5. 用户故事收敛

近期活动里出现了很多故事。战略上只把下面 7 条收进 MVP 方向，其余留作后续。

### 故事 1：一句话创建单次日程

- **作为** 正在路上或刚结束沟通的职场用户
- **我希望** 说“明天上午十点客户拜访，A 座 1503”就能创建日程
- **以便于** 我不用打开 App 逐项填写，也不用担心回头忘记地点

验收例子：

- **Given:** 当前没有同名同时间日程
- **When:** 用户说“明天上午十点客户拜访，A 座 1503”
- **Then:** 系统创建日程，语音反馈时间和标题，并在 IM 回执中保留地址

### 故事 2：创建周期提醒

- **作为** 有固定习惯或固定任务的个人用户
- **我希望** 说“每周五下午五点提醒我提交周报”就能建立周期提醒
- **以便于** 我不用每周重复创建同一件事

验收例子：

- **Given:** 用户没有同名周期提醒
- **When:** 用户说“每周五下午五点提醒我提交周报”
- **Then:** 系统创建每周五 17:00 的周期提醒，并反馈“下次提醒是本周五下午五点”

### 故事 3：查询今天、本周和刚记下的事项

- **作为** 对今天安排和刚才录入内容不放心的用户
- **我希望** 能问“我今天有什么事”“这周还有哪些提醒”“明天上午那个客户地址再说一遍”
- **以便于** 我不用打开日历，也能确认系统确实记住了关键细节

验收例子：

- **Given:** 用户今天还有 3 个日程，并且刚创建“明天上午十点客户拜访，A 座 1503”
- **When:** 用户问“我今天还有什么事”
- **Then:** 系统语音播最近几条和总数，完整列表发到 IM；用户追问地址时，再回答“A 座 1503”

### 故事 4：修改已有事项

- **作为** 经常临时改安排的用户
- **我希望** 说“把这周五的周报改到星期六上午十点”
- **以便于** 我不用删除后重建，也不会误改以后每周的规则

验收例子：

- **Given:** 用户有“每周五下午五点提交周报”的周期提醒
- **When:** 用户说“把这周五的周报改到星期六上午十点”
- **Then:** 系统只修改本周这一次，并反馈“下周仍然是星期五下午五点”

### 故事 5：跳过一次周期事项

- **作为** 有周期事项但临时不用执行的用户
- **我希望** 说“这周的周报跳过一次”
- **以便于** 我取消本次提醒，但不影响下一次周期

验收例子：

- **Given:** 用户有“每周五下午五点提交周报”的周期提醒
- **When:** 用户说“这周的周报跳过一次”
- **Then:** 系统标记本周这一条为跳过，并反馈“下次仍然是下周五下午五点”

### 故事 6：删除日程并可撤销

- **作为** 临时取消安排的用户
- **我希望** 能说“删掉今天下午三点和 Alex 的会”
- **以便于** 我快速清理已经取消的安排，并在删错时马上恢复

验收例子：

- **Given:** 用户有唯一一条“今天下午三点和 Alex 开会”
- **When:** 用户说“删掉今天下午三点和 Alex 的会”
- **Then:** 系统删除该日程，并反馈“已删除，可以说撤销恢复”

### 故事 7：提醒触发时即时处理

- **作为** 正在忙的用户
- **我希望** 提醒响起时直接说“知道了”“十分钟后再提醒”
- **以便于** 我不用打开 App，也能处理当前提醒状态

验收例子：

- **Given:** 系统正在主提醒“14:30 客户拜访”
- **When:** 用户说“十分钟后提醒我”
- **Then:** 系统只把这条提醒延后 10 分钟，不修改底层日程，并反馈新的提醒时间

边界例子：

- 用户说“把会议改到今晚八点”时，系统进入已有日程变更流程。
- 用户说“今天这次不参加了”时，系统进入周期实例变更流程。
- 有明确开始时间的日程可以在开始前 15 分钟给一条弱提醒；弱提醒只做预告，不要求用户回应，也不替代主提醒。

## 6. 本期要什么

本期不追求“会聊很多”，只跑通一条可靠的语音日程主流程：

1. 用户可以用语音创建单次日程，至少支持标题、日期、时间、地点/备注；会议、拜访、课程这类会占用时间段的日程，需要拿到结束时间或持续时长。
2. 用户可以用语音创建周期提醒，至少支持每天、每周、每月三类常见规则。
3. 系统只追问缺失信息，例如缺时间就问时间，不让用户从头重说。
4. 系统对低风险动作使用短反馈，例如“好，明天八点提醒你吃药”。
5. 系统对高风险动作使用显式确认，例如删除、覆盖、永久停止周期提醒。
6. 用户可以用语音查询今天、某一天、某一周、某一月、今年，以及刚刚创建的小事或日程；语音只播摘要，完整列表通过 IM 展示。
7. 用户可以修改单次日程，也可以修改周期事项中的某一次。
8. 涉及周期事项时，系统必须区分本次、之后全部、整个系列。
9. 用户可以跳过一次周期事项，并保留下一次提醒。
10. 用户可以删除日程，删除后提供短时间撤销。
11. 主提醒默认在用户指定提醒时间触发，并通过语音和 IM 同时发送；有明确开始时间的日程可以提前 15 分钟给一条弱提醒，弱提醒只做预告，不要求回应。
12. P2 只支持关闭提醒和稍后提醒；“已处理”“忽略本次”不作为 P2 命令，避免和完成事项、跳过周期实例混在一起。
13. 提醒触发时，如果用户说“改到某时间”“今天跳过”“停止后续”，系统进入已有日程变更流程，并按高风险规则确认影响范围。
14. 每次创建、提醒处理、修改、删除、跳过都留下 IM/文本回执，方便用户事后确认。
15. 提醒播报按内容复杂度分层：语音默认只播标题和时间；用户说“再详细说说”时，再补充地点和备注；完整详情写入 IM 回执。

## 7. 本期明确不做

| 维度 | 本期不做 | 原因 |
| --- | --- | --- |
| 专用设备 | 不做智能音箱、耳机、可穿戴或车载设备，也不讨论语音入口具体载体 | 8 周内验证交互价值，设备问题后置 |
| GUI | 不设计图形界面，不把页面、按钮、日历视图作为产品能力假设 | 本期验证语音入口和 IM 回执，不让评审转向界面方案 |
| 全天候监听 | 不做静默捕获、被动录音、自动判断哪句话值得记 | 隐私和信任成本太高，且不是日程管理的最短路径 |
| 个人记忆库 | 不做密码、取件码、长期记忆、跨天模糊检索；停车位置这类小事只在用户主动说出且非敏感时短期保存 | 避免扩成个人记忆助手，同时保留“帮我记一件小事”的轻量入口 |
| 位置与传感器 | 不依赖位置、摄像头、传感器，也不做“到楼下买牙膏”“到银行提醒取钱” | 本期只处理用户主动说出的安排，不处理环境感知 |
| 外部信号触发 | 不做“老张三点没回消息就提醒我” | 需要接入 IM/邮件等外部系统并持续监控 |
| 团队协作 | 不做共享日历、邀请他人、家庭成员所有权、会议室冲突 | 权限和协作规则会把个人产品变成团队产品 |
| 医疗产品 | 不做用药依从性、病情管理、照护判断 | 可以做普通提醒，不能承诺医疗效果 |
| 商业模式 | 不写订阅、设备销售、SaaS API 作为本期决策 | MS1 先证明 MVP，不做商业路线展开 |
| 通用 AI 助理 | 不做天气、闲聊、知识问答、会议纪要、自动总结 | 会冲淡“语音日程管理”的验证重点 |

## 8. 关键取舍

| 决策 | 备选方向 | 本期选择与理由 |
| --- | --- | --- |
| 产品边界 | 普通闹钟提醒 / 语音日程提醒工具 / 个人秘书 / 个人记忆助手 | 选“语音日程提醒工具”。它比普通闹钟多了查询、修改、删除、跳过和周期范围控制，但不扩成个人秘书或个人记忆助手 |
| 产品形态 | 语音入口 + IM 持久确认 / 面向用户的日历 GUI / IM 独立日历管理入口 | 选“语音入口 + IM 持久确认”。语音负责操作，IM 负责可回看记录、确认、撤销和异常修复，不把 IM 扩成完整日历产品 |
| 交互原则 | 默认确认 / 默认不确认 / 按风险分层确认 | 选按风险分层。普通创建用短反馈，删除、永久停止、范围不明必须确认 |
| 提醒播报 | 全量读出 / 简单短播、复杂先摘要 / 全部只写文本 | 选简单短播、复杂先摘要。语音要短，但复杂事项不能只靠一句话带过，详情交给 IM 回执 |
| 默认提醒时间 | 准时主提醒 / 固定提前 15 分钟 / 主提醒 + 可选弱提醒 | 选主提醒按用户指定时间触发；有明确开始时间的日程可以提前 15 分钟弱提醒，但弱提醒不替代主提醒 |
| 提醒响应 | 关闭和稍后 / 加上忽略与已处理 / 直接改日程 | 选关闭和稍后。“已处理”“忽略本次”容易被理解成事项完成或跳过周期实例，放到后续或 P3 判断 |
| 周期事项 | 本期不做 / 只做简单周期 / 做完整 RRULE | 选简单周期 + 清楚范围。每天/每周/每月够用，先把“本次/以后/整个系列”讲清楚 |
| 删除和修改 | 用户说了就执行 / 所有都二次确认 / 明确命中执行、歧义确认 | 选明确命中执行、歧义确认。语音要快，但不能赌用户想法 |
| 回执 | 只语音播报 / 只文本记录 / 语音短反馈 + IM 回执 | 选语音短反馈 + IM 回执。语音听过即逝，回执能降低不放心和误操作成本 |
| 冲突处理 | 本期不做 / 冲突时拒绝 / 提示冲突后允许用户确认 | 选提示后确认。用户可能故意保留重叠安排，系统不应替他决定 |

## 9. MVP 核心假设

> 对于有零散事项和周期提醒需求的用户，如果一款语音日程提醒工具能做到“说得快、问得少、错了能改、删改可撤销”，它就可能比打开日历 App 更适合临时录入和临时变更日程。

这个假设有三层：

1. **语音入口有价值**：用户在走路、做饭、开会间隙、通勤等场景下，愿意用一句话创建或处理提醒。
2. **风险控制决定信任**：用户真正害怕的不是多说一句，而是系统听错后静默误删、误改、误停周期提醒。
3. **回执降低记忆负担**：语音反馈听完就过去了，IM/文本回执能让用户事后确认“到底记了什么、改了什么”。

反证条件：

1. 用户认为打开日历 App 比语音更快、更安心。
2. 多数真实表达都需要两轮以上澄清，语音效率不成立。
3. 用户不信任系统处理删除、修改、周期范围，频繁回 App 检查。
4. 周期提醒、跳过一次、改本次这些场景频率不够高。
5. IM 回执无人查看，无法降低语音听过即逝的问题。

如果出现这些反证，应先缩小到“语音创建提醒”单点，不继续扩展高级故事。

## 10. 已确认的 Proposal 地图

三份 Proposal 已经提交，并在 [PR #59](https://github.com/1024XEngineer/XE6-15/pull/59) 做过整合。战略文档这里不展开完整 Proposal，只保留已经确认的边界。

```text
Proposal 1：语音创建与查询
建立可被确认、能查回来的日程和短期小事
        |
        +--> Proposal 2：提醒触发与即时响应
        |    处理提醒本身，只支持关闭和稍后
        |
        +--> Proposal 3：已有日程变更与周期控制
             修改事项、周期实例和周期规则

公共交互规则：
语音短反馈 + IM 回执 + 冲突提示 + 风险分级确认 + 可撤销记录
```

实施顺序仍然建议 P1 -> P2 -> P3，因为 P1 先建立日程，P2 和 P3 才有对象可处理。但能力依赖上，P2 和 P3 都建立在 P1 之上，彼此不是严格前后关系。

当前口径只保留三条：

1. **P1：语音创建与查询**：解决“用户能否快速录入日程，并确认系统正确记录”。本阶段支持单次日程、每天/每周/每月简单周期、主动说出的非敏感短期小事，以及今天、某一天、某一周、某一月、今年和刚创建事项查询；任意关键词模糊查询先不进入。
2. **P2：提醒触发与即时响应**：只处理当前提醒本身。主提醒按用户指定提醒时间触发；有明确开始时间的日程可以提前 15 分钟给一条弱提醒。用户响应只保留关闭和稍后，不把“已处理”“忽略本次”放进 P2。
3. **P3：已有日程变更与周期控制**：处理所有会改变已有日程内容、某次周期实例或整个周期范围的动作，例如修改、跳过、暂停、终止、删除、范围确认和撤销。用户接受冲突时可以保留冲突日程，用户拒绝时不留下日程、提醒或回执。

## 11. 验收标准

战略文档通过的标准不是“内容看起来完整”，而是团队能同意下一步验证什么。

评审先确认三件决策：

1. 最终定位是语音日程提醒工具，不扩成个人秘书或个人记忆助手。
2. 本期不做面向用户的日历 GUI，不依赖位置、摄像头、传感器，不做被动记忆和共享日历。
3. 语音是主操作入口；IM 负责可回看记录、确认、撤销和异常修复，但不作为独立日历管理入口。

后续原型验证至少要看这些指标，具体阈值在测试方案中另定：

1. 创建日程的任务完成率。
2. 用户从说出安排到确认完成所需的时间。
3. 平均需要几轮澄清。
4. 日期、时间和周期范围的记录错误率。
5. 用户是否还需要打开其他日历检查。
6. 修改周期事项时，用户是否理解影响的是本次、之后全部还是整个系列。
7. 同一事项用语音完成，是否比现有日历操作更快。
8. IM 回执是否被查看，以及是否帮助用户发现或恢复错误。
9. 文档只做战略和产品边界判断，不提前写具体实现细节。
