# XEngineer 实习生时间管理应用用户故事

这版用户故事把产品定位从“普通待办工具”收回到“以 GitHub 为项目中心的训练营时间管理”。结论是：时间管理要围绕 Milestone、Issue、PR、Review、会议和日报这些真实工程动作展开，下一步可以据此收敛 Proposal 和原型范围。

## 1. Review 后的调整方向

- **GitHub 是项目中心**：所有时间计划都要落到 Milestone、Issue、PR、Review 或 Wiki 上，而不是另起一套孤立待办。
- **补上项目启动阶段**：项目一开始就要设目标、拆任务、做投入规划，否则后面的会议、汇报和复盘都没有共同上下文。
- **预警看产出偏差**：不是简单提醒“超时了”，而是判断“预计产出和实际推进不匹配”。
- **偏离后要能改行动项**：预警之后，系统要帮助用户重排今日任务、顺延低优先级事项，必要时砍需求。
- **汇报、求助、会议、Review 都要回 GitHub**：这些不是零散文本，而是项目推进的一部分。

## 2. 目标用户

目标用户是 XEngineer 训练营里的实习生/学员，包括组长和普通组员。

他们不是普通自律用户，也不是成熟项目经理。他们第一次按真实工程流程推进一个项目：要写 Proposal、拆 Issue、开 PR、接受 Review、发日报、做路演。真正困难的地方不是“不知道要努力”，而是不会把这些工程动作变成可执行、可复盘的时间计划。

## 3. 用户故事

### 故事 1：【项目目标入 GitHub】—— 先把模糊题目变成可推进的项目上下文

对应痛点：项目刚开始时只有一个大方向，没有沉淀成 GitHub 里的目标、边界、阶段计划和任务拆分。

角色：小明，第一次从 0 到 1 推进真实产品落地的训练营组长。

真实场景：开题第一天，导师讲了业务背景：时间管理 App 要服务训练营实习生，要结合 GitHub 项目过程，不要做普通待办或番茄钟。小明听完觉得方向大概懂了，但会后只在群里发了几句总结。

两天后，组员开始各写各的。有人查习惯打卡，有人做会议助手，有人想做 AI 自动排期。大家都很忙，但已经偏离导师最初要求。

系统触发：小明新建项目时，系统发现 GitHub 里还没有 Milestone、Proposal Issue、目标用户和不做清单。

原型的用户故事表达：

作为一个刚开始带项目、容易把导师输入散落在聊天里的训练营组长，  
当我拿到训练营业务议题时，  
我希望系统引导我把目标用户、核心问题、8 周交付、阶段里程碑、任务拆分、负责人、截止时间和预计投入时间沉淀为 GitHub Project、Issue 或 Wiki 内容，  
以便于后续代码提交、会议结论、PR、日报和复盘都围绕同一份项目事实推进，而不是边做边补、越做越乱。

用了之后的爽点：以前会议一结束，信息就散了。现在项目一开始，GitHub 里就有一份大家都能指向的项目上下文。

### 故事 2：【目标拆成 Issue】—— 不要只写“完成 Proposal”，要知道今天交什么

对应痛点：阶段目标太大，没有拆成可执行 Issue，也没有预期产出和投入规划。

角色：小华，负责 MS1 产品设计的组员。

真实场景：MS1 的目标写着“完成战略决策、产品 Proposal、架构主干和首个可串联版本”。小华知道这很重要，但不知道今天到底该干什么。她在待办里写了“写 Proposal”，估时 2 小时。

写到一半她才发现，Proposal 下面还包括目标用户、真实场景、竞品参考、不做范围、验收标准。2 小时根本不够，架构同学也不知道什么时候能拿到产品边界。

系统触发：系统发现 Milestone 下只有大任务，没有拆成带预期产出的 GitHub Issue。

原型的用户故事表达：

作为一个第一次按 Milestone 推项目的训练营组员，  
当我只写了“完成 Proposal”这种大任务时，  
我希望系统帮我把它拆成 GitHub Issue，例如“确认目标用户”“整理真实用户故事”“写不做清单”“补验收标准”“组内 Review”，并要求每个 Issue 填预期产出、截止时间和预计投入，  
以便于我不是对着一个大目标发呆，而是知道今天应该交出哪一块东西。

用了之后的爽点：以前我觉得“写 Proposal”是一件事。拆完才知道，它其实是几个要分别交付、分别验收的小任务。

### 故事 3：【投入优先级】—— 一天做很多事，不等于项目真的往前走

对应痛点：任务已经很多，但用户不会判断哪个 Issue 最值得先投入。

角色：小周，手里同时有调研、原型、日报和接口讨论的普通组员。

真实场景：周一早上，小周打开看板，发现自己有 7 个 Issue：竞品补充、用户故事改写、原型草稿、会议记录、PR Review、日报、接口命名讨论。每个都看起来该做。

以前他会先做简单的。到晚上才发现，真正卡住团队的是“用户故事改写”，因为架构同学等这个边界开工。

系统触发：系统读取 Milestone、Issue 依赖和截止时间，发现“用户故事改写”是架构 Issue 的前置条件。

原型的用户故事表达：

作为一个任务很多、但不擅长判断投入优先级的训练营组员，  
当我准备安排今天时间时，  
我希望系统根据 GitHub 依赖关系告诉我：“今天最该投入的是 Issue #8 用户故事改写，预计 3 小时，因为它阻塞 Issue #14 架构骨架；竞品截图可以顺延；日报只需 20 分钟收口。”  
以便于我不是挑最容易的任务做，而是把时间投到最影响项目推进的位置。

用了之后的爽点：以前我一天做了很多小事，项目却没动。现在系统会提醒我先做那个能解锁别人工作的 Issue。

### 故事 4：【推进偏离预警】—— 不是“你超时了”，而是“该出现的产出没出现”

对应痛点：只看耗时不够，真正的问题是预期产出和实际推进不匹配。

角色：小琪，负责写用户故事文档的组员。

真实场景：小琪给 `Issue #8 用户故事改写` 估了 4 小时，预期产出是“至少 6 个能解释原型价值的真实用户故事”。她周二已经投入 6 小时，文档也写了很多字，但里面大多是用户画像、痛点和需求点，真正像样的用户故事只有 1 个。

如果系统只看“花了 6 小时”，它只能说超时。问题是：她没有产出该产出的东西。

系统触发：系统对比 Issue 的预期产出、文档结构和实际内容，发现故事数量不足、GitHub 场景缺失、仍停留在需求清单。

原型的用户故事表达：

作为一个容易把“写了很多”误认为“推进了很多”的训练营组员，  
当我投入时间已经超过预估，但预期产出还没出现时，  
我希望系统直接提示：“Issue #8 不是单纯超时，而是产出偏差。预期：6 个 GitHub 项目推进故事；实际：用户画像和需求点较多，故事不足。建议下一步：停止扩写画像，先补项目目标入 GitHub 和目标拆成 Issue 两个故事。”  
以便于我知道问题不只是慢，而是方向偏了，能马上调整行动项。

用了之后的爽点：以前我写了很多还被打回，会觉得委屈。现在系统告诉我偏差在哪里，我知道该删什么、补什么。

### 故事 5：【偏离后重排】—— Review 打回后，今天的计划要立刻变

对应痛点：发现偏离后，没有把新情况转成新的任务和时间安排。

角色：小华，被导师连续指出用户故事不像用户故事的组员。

真实场景：周三下午，导师在 PR Review 里说：“不是用户故事。GitHub 在哪里？项目开始设目标和拆分任务规划没有覆盖。”小华知道要改，但她今天还排着原型、竞品截图和会议纪要。

以前她会把所有任务都往晚上挤，最后每件事都半成品。

系统触发：系统读取 Review 评论，识别出这是方向性返工，不是小修；原计划里的原型任务依赖用户故事通过。

原型的用户故事表达：

作为一个被 Review 指出方向偏差、但还想硬撑原计划的训练营组员，  
当导师评论明确要求补“GitHub 项目中心”和“任务规划故事”时，  
我希望系统把今天计划自动重排：“取消今晚原型打磨；新增 2 小时修正故事主线；新增 30 分钟对照 Review 自检；竞品截图顺延。当前首要目标是让 Issue #8 达到可进入架构讨论的状态。”  
以便于我不是在旧计划上继续加班，而是按新风险调整行动。

用了之后的爽点：以前被打回后，我只会焦虑。现在系统把返工变成新的行动清单，今天该干什么很清楚。

### 故事 6：【卡点记录回到 Issue】—— 求助不是另写小作文，而是带着项目上下文问

对应痛点：卡点记录和项目推进脱节，复盘和求助都要重新翻聊天记录。

角色：小林，负责 GitHub 同步接口的后端组员。

真实场景：小林在 `Issue #21 同步 GitHub Issue 状态` 上卡住了。他试了 API token、分页、状态过滤，折腾 3 小时。晚上要向导师求助时，他只记得“GitHub API 有点问题”，具体报错、试过什么、卡在哪个 Issue 上都散在终端和聊天里。

系统触发：系统发现某个 Issue 的工作时间连续超过预估 150%，但没有新增 commit、comment 或 PR。

原型的用户故事表达：

作为一个遇到技术卡点但不擅长整理问题的训练营组员，  
当我在某个 GitHub Issue 上投入很久却没有推进证据时，  
我希望系统提示我把卡点记录回写到这个 Issue：问题现象、报错、试过的方案、当前猜测、需要谁帮忙，并生成一段求助文本，  
以便于我向导师或队友求助时，不是重新解释背景，而是直接让对方看到项目上下文。

用了之后的爽点：以前求助像重新讲一遍案情。现在卡点就在 Issue 下，别人一眼能接上。

### 故事 7：【会议推进与方向校准】—— 会议不是开完就行，要把讨论拉回项目主线

对应痛点：会议、汇报和求助缺少 GitHub 项目上下文支撑，讨论容易停留在零散描述或功能清单。

角色：小明，缺少会议推进经验、需要担任项目会议推进人的训练营组长。

真实场景：组内开会讨论“时间管理 App 要不要做会议助手”。大家说了很多：有人觉得会议推进很痛，有人觉得偏题，有人说先做日报。会议看起来很热闹，但讨论没有围绕目标用户、核心痛点和当前 Milestone 展开。

会后群里只有一段零散纪要，没有形成 GitHub Issue，也没有明确谁负责、什么时候交。

系统触发：会议开始前，系统读取当前 Milestone、Project 状态和阻塞 Issue；会议过程中检测到讨论议题偏离当前目标；会议后检测到没有新增或更新任何 Issue。

原型的用户故事表达：

作为一个缺少会议推进经验的训练营组长，  
当我组织项目会议时，  
我希望系统在会前基于 GitHub 项目计划帮我列出会议目标、关键议题和需要形成的决策；在会议中提醒我把讨论拉回目标用户、核心痛点和当前 Milestone；会后把结论、未解决问题和待办关联到 GitHub Issue 或 Project，  
以便于会议不只是聊完，而是真的推动团队形成共识并推进项目。

用了之后的爽点：以前会开完了，事情还在空气里。现在结论会落到 Issue 上，谁负责、什么时候交都清楚。

### 故事 8：【投入报告生成】—— 日报不是“今天很忙”，而是投入和产出的对账

对应痛点：日报没有链接、没有产出、没有风险，导师看不到项目真实推进状态。

角色：小周，每天都忙但日报写得很虚的组员。

真实场景：小周晚上要发日报。他今天查了资料、改了文档、回了 Review、卡了一个接口问题。最后他写：“今天继续推进前端页面，处理了一些问题。”导师看不出他推进了哪个 Issue，也看不出哪里需要帮忙。

系统触发：系统读取小周当天绑定过的 Issue、PR、Review 评论、时间块和卡点记录。

原型的用户故事表达：

作为一个不会把一天工作讲清楚的训练营组员，  
当我需要发日报或向导师同步进度时，  
我希望系统按 GitHub 对象生成投入报告：“今日投入 6 小时：Issue #8 用户故事修正 2.5 小时，产出故事 2 个；PR #32 Review 返工 1.5 小时，剩余阻塞评论 1 条；Issue #21 GitHub API 同步卡住 1 小时，已记录求助信息。明日优先级：先解 #21，再复审 #32。”  
以便于导师和队友看到的不是流水账，而是项目推进状态、风险和下一步计划。

用了之后的爽点：以前日报像补作业。现在日报是投入和产出的对账单，我自己也能看出今天有没有真正推动项目。

### 故事 9：【Review 返工入计划】—— 评论不是聊天，是新的时间账单

对应痛点：PR Review 后知道要改，但不知道哪些必须立刻改、要花多久、会影响谁。

角色：小兰，负责前端 Dashboard 的组员。

真实场景：小兰开了 PR `#32 Dashboard 任务风险视图`。组内 Review 留了 12 条评论：有 3 条是命名问题，4 条是 UI 小问题，2 条是验收标准没覆盖，还有 3 条会影响后端接口。小兰知道要改，但她把这些都当成“晚上顺手处理”。

结果 PR 两天没合，后端联调也被卡住。

系统触发：系统读取 Review 评论，识别阻塞类评论、非阻塞类评论和建议类评论，并估算返工投入。

原型的用户故事表达：

作为一个低估 Review 返工成本的训练营组员，  
当我的 PR 收到多条 Review 评论时，  
我希望系统把评论转成返工计划：“必须今天处理 3 条阻塞评论，预计 1.5 小时；2 条验收标准需要补测试，预计 1 小时；UI 建议可放到下个 Issue。该 PR 阻塞后端联调，建议优先处理。”  
以便于我知道哪些评论会影响交付，不会把 Review 当成额外小事拖着。

用了之后的爽点：以前 PR 开了我就觉得快完成了。现在我知道，Review 处理完、PR 合进去，才算真的交付。
