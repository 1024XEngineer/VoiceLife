# 个人项目管理工具：MS1 战略决策

> 状态：工作稿，待组内评审<br>
> 日期：2026-07-13<br>
> 对应工作项：[XE6-15 Issue #7](https://github.com/1024XEngineer/XE6-15/issues/7)<br>
> 证据截止：2026-07-13 16:25（UTC+8）

本期决定做一款面向 XEngineer 训练营成员的 GitHub 个人项目管理工具：只读取与当前用户直接相关的 Issue、PR 和 Review 行动，把它们收成个人任务池，给出今日优先顺序，并在任务未完成或 GitHub 状态变化后提出重排建议。

请组内确认四项决策：目标用户、GitHub-only 数据边界、不做团队协作，以及按“任务池导入 -> 优先级排序与展示 -> 任务重排”依次拆成三个 Proposal。确认后再分别细化 Proposal 和原型，本期不继续扩日报、语音输入、长期倒排等方向。

## 1. 战略决策摘要

| 决策项 | 本期选择 |
| --- | --- |
| 做什么 | 把 GitHub 中与本人相关的 Issue、PR 和 Review 行动收成个人任务池，给出今日顺序，并在计划偏离后帮助恢复 |
| 为谁做 | 已有 GitHub 账号、属于训练营 Organization、正在用 Issue / PR 推进项目的 XEngineer 成员 |
| 核心问题 | GitHub 记录了项目对象和提交过程，却没有直接回答“我今天先推进什么、哪个 PR 要处理、计划被打断后怎么重新排” |
| 价值主张 | 用户登录后先看到自己的行动清单和排序理由，不必逐个仓库、Issue、PR 和 Review 页面翻找；计划失效时也不用从头整理 |
| 数据边界 | GitHub 是唯一项目任务来源和状态事实源；工具只保存个人排序、最小计划信息和确认记录，不再建立一套独立项目任务系统 |
| 产品形态 | 用 GitHub 登录的独立个人视图。GitHub-only 约束数据来源，不要求界面必须嵌在 GitHub 页面内 |
| 不做什么 | 不做组织或团队管理，不建立第二套共享任务系统，不扩成通用时间管理、GitHub 客户端或全自动 AI 排程工具 |
| MVP 主线 | 导入与我相关的任务 -> 解释为什么先做这些 -> 未完成或状态变化后给出新顺序 -> 用户确认 |

### 1.1 我们要什么

本期不追求功能多，而是先跑一条个人真实会用、也能用 GitHub 数据验证的最短路径：

1. 要一个足够窄、团队真正理解的用户群，只服务正在参加 XEngineer 项目的个人贡献者。
2. 要从个人视角回答问题，首页先回答“现在轮到我做什么”，而不是先展示团队全貌。
3. 要把 Issue、本人 PR、待处理 Review 统一成一种“个人行动”，减少用户在不同 GitHub 页面之间来回翻找。
4. 要只收与本人有直接行动关系的对象，不把 Organization 中所有公开任务都塞进任务池。
5. 要区分“项目对象”和“下一步行动”。一个 PR 可以对应“补修改”“回复评论”或“等待 Review”，不能只显示 PR 标题。
6. 要给出今日 1-3 个优先行动，让用户能从任务池直接进入执行，而不是面对另一张长列表。
7. 要解释每个排序结果，说明它为什么排在前面、缺了哪些信息，避免用户被黑盒分数支配。
8. 要允许用户手动调整顺序。系统负责建议，最终取舍仍由用户决定。
9. 要在未完成、Review 返工、阻塞变化或方向调整后给出恢复方案，而不只是显示“已延期”。
10. 要容忍 GitHub 元数据不完整。缺 assignee、截止时间或 Priority 时，先明确暴露缺口，再请求最小确认。
11. 要让真实工作继续留在 GitHub。用户从本工具看见行动后，仍回到原 Issue、PR 或 Review 页面处理。
12. 要用 XE6-15 和非本组学员的真实任务验证覆盖率、排序可信度和重排可信度，再决定是否继续扩展。

### 1.2 我们不要什么

1. 不要再做一款面向所有人的普通待办、日历或时间管理 App。
2. 不要把目标用户扩大到导师、组长、项目经理或整个 Organization 的管理者。
3. 不要做团队任务分派、Reviewer 调度、成员负载、绩效排名和组织进度总览。
4. 不要把 GitHub、日历、聊天、邮件、文档和生活待办一次性聚合起来。
5. 不要在产品里建立一套与 GitHub 并行的共享 Issue、PR 或工作流。
6. 不要替代 GitHub 的编辑、评论、Review、合并、Release 和权限能力。
7. 不要让 AI 猜测截止时间、黑盒决定优先级或未经确认自动修改计划。
8. 不要自动修改共享仓库、催办他人、发送延期通知或代表用户完成协作动作。
9. 不要在本轮做长期倒排、完整日历、甘特图、时间块和跨成员资源排程。
10. 不要扩展日报、周报、会议助手、语音输入、文件导入和通知中心。
11. 不要加入番茄钟、习惯打卡、锁机、奖励、社交等通用效率功能。
12. 不要在 GitHub-only 假设尚未验证前，同时开发三个 Proposal 或继续增加第四条产品主线。

这不是一个普通待办 App，也不是 GitHub Projects 的替代品。它只补 GitHub 原生工作流中的个人决策层。

## 2. 关键取舍

| 决策 | 备选方向 | 本期选择与理由 |
| --- | --- | --- |
| 用户视角 | 个人推进 / 团队管理 / 组织管理 | 只做个人推进。用户只关心自己要推进或处理的对象，团队管理会引入分派、权限、负载和管理者视图，偏离 8 周 MVP |
| 任务来源 | GitHub-only / GitHub 加日历、聊天、手工任务 / 通用待办 | 先选 GitHub-only。目标用户的项目过程会留在 GitHub，单一来源最容易验证；代价是必须接受并测试信息缺失风险 |
| 产品界面 | GitHub 原生 Project / 嵌入式扩展 / 独立个人视图 | 先用独立个人视图验证排序和重排体验，但所有项目对象仍跳回 GitHub 处理。最终容器由后续架构和权限验证决定 |
| 优先级 | 纯手工 / 黑盒自动排序 / 透明建议加手动调整 | 选择透明建议加手动调整。每一项说明排序理由，用户保留最终决定权 |
| 重排 | 自动改计划和共享数据 / 只告警 / 给出建议并确认 | 选择“建议并确认”。只告警没有下一步，自动执行又会过早拿走控制权 |
| 截止时间缺失 | AI 猜测 / 强制填表 / 暴露信息不足并做最小确认 | 本期不让 AI 猜。先用现有 Milestone、Review 和状态信号；确实缺字段时只要求一次最小确认，并保存为个人计划信息 |


## 3. MVP 核心假设

> 对于已经在训练营 Organization 中用 GitHub 推进项目的成员，仅使用与本人直接相关的 Issue、PR 和 Review 信号，可能覆盖主要当前项目行动；在此基础上，透明的今日排序和未完成任务重排，可能减少每天翻找任务、判断先后和计划失效后重新整理的成本。

“只用 GitHub”在本稿中有三个明确含义：

1. GitHub 是项目任务、交付状态和协作记录的事实源。
2. 工具可以保存个人排序、预计投入、完成确认和重排历史，但这些只是派生计划，不是另一套共享项目任务。
3. 界面可以是独立 App；“只用 GitHub”不等于“所有交互必须发生在 GitHub 页面里”。

它也有清楚的反证条件：如果 GitHub 不能覆盖大部分真实行动，关键排序字段长期缺失，或者用户仍觉得 GitHub 原生页面更快，那么这条产品方向不成立。此时应停下来改假设，不应继续给三个 Proposal 堆功能。

## 4. 要什么，不要什么

### 4.1 本期要什么：最小闭环

1. 用户用 GitHub 登录，选择训练营 Organization 下的一个项目仓库。
2. 授权页说清读取范围、失败原因和撤销方式；首轮只申请生成个人任务池必需的权限。
3. 系统只读同步与当前用户直接相关的开放 Issue、本人 PR 的待处理动作、请求本人 Review 的 PR。
4. 同一个 GitHub 对象只出现一次，但可以明确显示当前行动是“推进”“修改”“Review”还是“等待”。
5. 系统把不同 GitHub 对象归一成个人任务池，保留仓库、类型、编号、标题、链接、状态、Milestone、更新时间和“为什么轮到我”。
6. 同步失败、权限不足或字段缺失时明确告诉用户，不用空列表或猜测结果冒充正常状态。
7. 首页既能查看完整个人任务池，也会突出今日 1-3 个建议行动，不让全量信息淹没当前选择。
8. 每个建议行动显示排序理由，例如“等待你回复 Review”“阻塞当前 Milestone”“昨日未完成”，而不只给一个分数。
9. 用户可以上调、下调、暂缓或拒绝建议；个人调整不写回团队共享优先级。
10. 今日任务未完成，或 GitHub 出现新 Review、阻塞、优先级等变化时，系统识别原计划已经失效。
11. 系统给出新的今天或明天顺序、变化原因和被挪动的任务；用户可以确认、修改或拒绝。
12. 用户点击行动后回到原 Issue、PR 或 Review 页面处理，完成状态再由 GitHub 同步回来。

### 4.2 本期明确不做

| 维度 | 本期不做 | 为什么现在不做 |
| --- | --- | --- |
| 目标用户 | 不服务不使用 GitHub 的用户，也不覆盖普通生活任务用户 | 这两类用户需要完全不同的任务来源和使用场景，无法验证 GitHub-only |
| 管理视角 | 不做导师、组长、项目经理和 Organization 管理者首页 | 本期问题是个人下一步，不是整个团队是否按计划推进 |
| 团队协作 | 不做任务分派、Reviewer 分配、成员负载、共享排期和团队优先级仲裁 | 这些能力需要多角色、权限、冲突处理和团队共识，属于另一条产品主线 |
| 绩效与监督 | 不做排名、工时比较、逾期问责和成员评分 | 它会改变产品关系，也会让个人助手变成管理工具 |
| 沟通 | 不做聊天、评论替代、审批流、催办和自动发送消息 | GitHub 和训练营群已经承载沟通，本产品不再造一个沟通入口 |
| 外部数据源 | 不导入日历、飞书、微信、邮件、Notion、Jira、网页或生活待办 | 多来源会把验证重点从个人排序变成集成工程 |
| 独立任务系统 | 不在 App 内创建只存在于本产品的共享任务 | GitHub 必须继续是项目事实源，否则用户要维护两份状态 |
| GitHub 写操作 | 不批量创建、修改、关闭 Issue，不提交 Review，不合并 PR | 首轮先证明读和排有价值，同时降低权限与误操作风险 |
| GitHub 替代 | 不复制 Issue、PR、Review、Project、Release 的完整详情和编辑能力 | 产品只补个人决策层，不重做 GitHub 客户端 |
| AI 自动化 | 不做 AI 自动拆解、黑盒打分、截止时间猜测和全自动排程 | 当前数据不足，用户信任也尚未验证；系统先给透明建议 |
| 自动协作动作 | 不自动改共享 Priority、指派他人、催办、发延期通知 | 个人计划不能擅自改变团队事实或代表用户作承诺 |
| 长期规划 | 不做 Milestone 倒排、复杂日历、甘特图、跨周容量和团队资源重排 | 713 会议已把长期倒推放到后续，本轮只验证今天与偏离恢复 |
| 时间执行 | 不做时间块、计时、番茄钟、锁机和专注模式 | “今天先做什么”尚未验证前，不扩到“如何保持专注” |
| 汇报与提醒 | 不做日报、周报、会议助手、独立复盘报表和通知中心 | 完成状态只作为重排输入，不在本期另做输出产品 |
| 输入形态 | 不做语音、文件、截图和自然语言批量导入 | 当前任务只来自 GitHub，不需要新增采集通道 |
| 覆盖范围 | 首轮不承诺跨 Organization、全账号多仓库、移动端和桌面端同时覆盖 | 先用一个真实仓库证明核心闭环，避免平台范围先于价值验证 |

## 5. 三个 Proposal 地图

```text
GitHub Issue / PR / Review
           |
           v
Proposal 1：任务池导入
           |
           v
Proposal 2：优先级排序与展示
           |
           v
Proposal 3：任务重排
           |
           v
用户确认新的个人行动顺序
```

三个 Proposal 有前后依赖，不是三项并行功能。前一个没有验证通过，后一个就没有可靠输入。

| Proposal | 要解决的窄问题 | 本期范围 | 明确不做 | 验收方向 |
| --- | --- | --- | --- | --- |
| 1. 任务池导入 | 用户不必逐页寻找自己要推进的 Issue 和要处理的 PR | GitHub 登录、选择一个仓库、只读同步、个人行动过滤、去重、来源链接和同步状态 | 多来源、组织全量视图、写回 GitHub、优先级和排程 | 与用户自报清单对照，验证覆盖率与准确度 |
| 2. 优先级排序与展示 | 有任务池后，用户仍不知道今天先做哪几件 | 今日 1-3 项、透明规则、排序理由、缺失信息提示、手动调整 | 黑盒 AI、团队优先级仲裁、长期倒排、修改 GitHub Priority | 用户能快速找出 Top 3，且多数结果只需调整 0-1 项 |
| 3. 任务重排 | 计划失效后，用户不知道如何恢复 | 未完成状态采集、Review/阻塞变化触发、今天/明天的新顺序、变化理由、确认或拒绝 | 自动改共享数据、自动催办、长期排程、团队资源重排 | 真实偏离场景中，用户理解并接受或轻调建议 |
