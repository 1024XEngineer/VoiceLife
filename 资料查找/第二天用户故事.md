# 第二天（2026-07-08）用户故事：调研交了，但项目没往前走

这条故事的判断是：XEngineer 学员需要按 Milestone、Issue 和 Review 判断调研是否真正推进项目，不能把“已开 PR”直接算作完成。

请组内确认它是否足以代表 7 月 8 日暴露的问题；本 Draft PR 只用于逐行评审，定稿后把结论回填 Issue #11，不合并。

## 用户场景：PR 交了，为什么我今天还得推倒重来

**对应痛点：** 个人计划只记了“查资料并提交 PR”，没有把当前 Milestone 的目标、Issue 的预期产出和 PR 的实际产出连在一起。文件提交后，用户很容易把任务当成“已完成”，等到 Review 或第二天会议才知道它没有推进阶段目标。

**用户角色：** 赵兴鹏，第一次按 XEngineer 工程流程推项目，负责抖音侧时间管理调研的普通组员。

**真实场景：**

7 月 7 日，我查了产品、理了功能，也把文档放进 PR #1。我下班时觉得这件事已经完成，第二天的计划是跟大家继续讨论基础功能和特异功能。

7 月 8 日早会，四个人的 PR 都打开了，我们却回答不了一个更基本的问题：到底为谁做？这些人在什么场景里真的很痛？导师在 Review 里问我“观点是什么”时，我才发现自己完成的是查资料这个动作，不是调研要支撑的产品判断。

这时原来的个人计划已经失效。如果我还照旧计划继续补功能点，只会花更多时间离 MS1 的产品判断更远。

**系统触发：**

应用读取当前 Milestone、我被分配的 Issue、关联 PR 及 Review。它发现“预期产出”中的目标用户、核心场景和调研结论没有对应证据，或 Reviewer 已明确指出方向问题时，将任务标记为“产出偏差”，而不是简单显示“已提交”或“已超时”。

**原型的用户故事表达：**

**作为**一名第一次按 GitHub 工程流程推项目的 XEngineer 学员，

**当**我已经为调研任务开了 PR，但 PR 的实际产出没有满足 Milestone 和 Issue 里的预期产出，或 Review 指出我的方向有误时，

**我希望**应用不要把“开了 PR”算作完成，而是沿着 GitHub 关联关系告诉我哪个阶段目标没有被推进、哪些产出仍然缺失，再把 Review 结论转成我当天的重排方案，

**以便**我停下低价值的继续扩写，先补目标用户证据、核心场景和明确结论，经过再次 Review 后再启动依赖它的 Proposal 任务。

**用了之后的感受：** 以前我是第二天开会被指出问题，才知道前一天忙错了。现在我在个人计划里就能看见：我交了什么，还欠什么，今天应该停哪件事、先补哪个产出。

这一天暴露的不是“调研做得太慢”，而是前一天已经提交了 PR，产出却没有回答 MS1 真正需要的目标用户、核心场景和产品判断。本故事建议应用以 GitHub 为项目事实来源，用 `Milestone -> Issue -> PR -> Review -> 个人重排 -> 再次验收` 把“交了文件”和“推进了目标”分开。

本 Draft PR 使用 `Refs #11` 关联决策任务，只确认场景是否真实、判断是否成立；当前文件不是已定稿 Proposal，也不会关闭 Issue #11。

## GitHub 在应用中的流程

| GitHub 对象 | 它提供的项目事实 | 应用如何转成个人时间管理 |
| --- | --- | --- |
| Milestone | MS1 要完成战略决策、Proposal 和首个可串联版本 | 先判断哪些任务真正推进本阶段，不让个人从“容易做”的事开始排 |
| Issue | 记录任务目标、预期产出、验收标准、负责人与依赖 | 只有当这些字段足以规划时，才生成个人时间块；缺字段时先提醒澄清 |
| PR | 提供真实提交、变更内容和更新时间 | 将实际产出与 Issue 的预期产出对账，不把 PR 创建本身当成完成 |
| Review | 记录通过、缺口、方向偏差和返工要求 | 区分小修与方向性返工，把后者立即纳入今日优先级和投入重排 |
| 新 Issue / Sub-issue | 保留方向调整的原因、新目标、责任人和验收条件 | 将“返工”变成可安排的新行动，而不是在旧计划上继续加班 |
| 再次 Review | 确认缺失产出已补齐，任务真正达到验收条件 | 解锁依赖任务，更新剩余时间和 Milestone 风险 |

对赵兴鹏来说，应用在 7 月 8 日应该给出的不是一个泛泛的“任务延期”红点，而是一份有 GitHub 依据的个人重排建议：

1. 暂停继续补充功能清单，因为它不再是当前最高优先级。
2. 将“调研结论缺目标用户与核心场景”标记为 PR #1 的产出偏差，保留原文档和 Review 证据。
3. 把 Issue #11 中的三个决策问题转成个人待办：候选目标用户是谁、证据是什么、其真实问题是什么。
4. 空出原本计划给“继续功能调研”的投入，由用户确认后改排给证据梳理、真实用户验证和组内决策。
5. 将此前调研提出的 ADHD 用户特征标记为“待验证假设”，不把它直接当成目标用户结论，也不在 Review 通过前解锁依赖它的 Proposal 任务。
