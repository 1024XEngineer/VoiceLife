# 语音模块与 SQLite 边界决策

一句话结论：旧 MVP 最值得迁移的是实时性和资源边界，不是它的应用状态机；新项目以 ESP32-S3 为首个 Profile，将音频数据面、Provider 控制面和 SQLite 业务控制面分离。
一句话动作：#113 已把 ESP32-S3 PCM Audio Port 跑到真实板；下一步补 Linx WSS 会话装配与 Opus，再根据受控声学证据决定 AFE/AEC，其他板卡仍只登记 Profile，不提前承诺可用。

## 1. 关键结论

1. 小智和旧 MVP 都采用独立输入、输出、编解码任务及有界队列；新代码把它们固化为 `BoundedAudioFrameQueue`。
2. Linx hello 后才打开硬件，capture/playback 格式必须分离；TTS abort 和重连必须使 generation 失效。
3. ESP-SR AFE 需要明确的 playback reference 才能进入设备 AEC 能力；当前板没有实测证据时只声明 AEC-0。
4. SQLite 统一协议只在业务控制面提供事务命令和结构化结果，不能让实时音频模块直接持有数据库连接。
5. “可迁移”定义为同一契约可被多个 Adapter 实现，不定义为一份固件覆盖所有 MCU。

## 2. 对抗性检查

- 仅凭源码队列参数能否证明播放无卡顿？不能；必须有实板欠载、延迟和最低堆证据。
- ESP32-S3 有两个 I2S 是否等于当前板支持全双工 AEC？不能；还缺 reference 线路、声学隔离和 AFE 结果。
- SQLite `commit` 返回成功是否等于掉电不丢数据？不能；VFS sync、文件系统、介质和断电方式必须一起记录。
- 是否应该马上加入 RP2350、STM32、nRF 等 Adapter？不应该。先让 ESP32-S3 的数据面和存储控制面通过真实准入，再以能力探针增加板卡。

## 3. 当前缺口

- `AudioInputPort` 已接入 Profile 驱动的 ESP32-S3 PCM/I2S Adapter，主机测试覆盖 10 ms period 到 60 ms 帧的组装；AFE、Opus 和物理声学闭环仍未接入。
- Runtime 仍未通过 Profile Factory 创建生产 Audio/Provider/Storage Adapter。
- SQLite `StorageTransactionPort` 尚未入主干；目前已固化为设计决策，实板 probe 另有仓库和证据。
- Linx WSS/ASR/TTS 云端闭环和真实 I2S/AFE/Opus 仍未验收。
